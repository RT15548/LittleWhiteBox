# 小白 Phone OS 目标开发文档

> 状态：执行基线
> 产品阶段：测试线首版，不为旧实验 UI 或内部路由保留兼容分支
> 当前目标：完成可长期承载 Tavern 功能的 Phone OS 壳，以及第一款精品 App「信息」

## 1. 文档使命

这份文档不是一次视觉改版清单，而是 Phone OS 后续开发、验收和取舍的长期基线。

Phone OS 的价值不只是提供手机通讯。它将成为 Tavern 内面向玩家的沉浸式功能入口：未来地图、任务、图鉴、相册等能力都应以 App 的形式进入同一套系统，而不是继续向聊天页面堆放独立按钮和浮层。

本阶段必须同时交付两件事：

1. 一套真正可扩展、可导航、可适配桌面与移动端的 Phone OS 平台壳。
2. 第一款完整、可信、能够代表后续品质标准的「信息」App。

开发过程中不以“功能已经能点”为完成标准。粗糙、虚假或不闭环的控件不得进入最终体验。

## 2. 产品北极星

玩家打开的不是网页里的一张消息卡片，而是一部属于当前剧情和当前会话的私人手机。

它应同时满足：

- **沉浸可信**：操作逻辑像真实手机，不暴露数据库、模型调用或网页组件的拼装感。
- **安静精致**：不复制现成 iOS，也不使用廉价霓虹“未来科技”装饰；每一层阴影、动效和间距都有明确目的。
- **剧情正确**：系统不得把现实设备时间伪装成剧情时间；剧情无法确认的内容宁可不显示。
- **平台可扩展**：新增地图 App 时只注册 App 和提供桥接，不修改 OS 导航核心。
- **双端原生感**：桌面端像拿起一部手机；移动端像进入一个全屏系统，不出现“手机套手机”。
- **状态可靠**：关闭手机、切换 OS 页面或等待后台生成时，不丢状态、不串会话、不重复提交。

## 3. 设计方向

### 3.1 气质

整体方向定义为：**静奢、私人、剧情内可信的随身设备**。

- 机身是低反射黑色珐琅与深灰金属，不靠夸张高光制造“高级感”。
- 系统界面以暖白、墨黑和克制的冷蓝为主，颜色优先表达层级和状态。
- 当前角色头像或会话视觉可以生成低饱和、强模糊的环境光晕，让每段剧情的手机拥有不同气息，但不得影响文字可读性。
- “小白”是系统品牌，不模仿现实手机厂商的商标、灵动岛或系统文案。
- 字体沿用 Tavern 已有的本地字体资产和排版体系，不引入外网字体。

### 3.2 记忆点

Phone OS 最应被记住的不是手机边框，而是：**每个剧情会话都有一部气质随角色变化、但操作始终稳定统一的私人设备。**

### 3.3 动效原则

- 手机打开：从触发位置轻微抬升并聚焦，时长约 220ms。
- App 打开：图标或卡片向内容层自然扩展，时长约 180ms。
- 页面前进/返回：方向明确，不同时使用缩放、位移和大面积模糊。
- 消息发送：先即时落下用户气泡，再进入等待状态。
- 所有核心动效支持 `prefers-reduced-motion`，降级后仍有清晰的状态变化。
- 动效不得阻塞输入、返回或关闭。

## 4. 产品边界

### 4.1 本阶段必须完成

- Phone OS 桌面、App 启动、App 内导航、返回、回到桌面和收起手机。
- 桌面端设备外壳与移动端全屏系统两种呈现模式。
- App 注册表与统一 App 生命周期边界。
- 第一款 App「信息」的联系人、搜索、添加联系人、会话列表、对话、发送、等待、失败和重试闭环。
- 正确处理软键盘、安全区、滚动、触控热区、焦点、Escape 和背景点击。
- 保持既有通讯持久化、剧情锚定、回滚、分支、角色档案和并发保护能力。
- 完整的源码测试、类型检查、构建验证和真实浏览器双端体验验收。

### 4.2 本阶段明确不做

- 不制作不能打开或没有真实功能的假 App。
- 不制作锁屏、密码、通知中心、控制中心等仅用于装饰的系统页面。
- 不展示现实系统时间，不伪造消息时间。
- 不为了模仿某个现实品牌保留灵动岛、假摄像头或不可交互 Home 条。
- 不在本阶段迁移地图、任务、图鉴的业务实现；只保证平台接口足以在后续接入。
- 不为当前测试线的旧 `phoneScreen` 路由或旧 DOM/CSS 结构保留兼容分支。

## 5. 信息架构与导航模型

```text
Tavern 聊天页
  └─ 打开 Phone OS
      ├─ OS 桌面
      │   └─ 信息 App 图标（可显示未读徽标）
      └─ App 舞台
          └─ 信息
              ├─ 会话列表
              │   ├─ 搜索
              │   └─ 添加联系人
              └─ 对话
                  ├─ 返回会话列表
                  ├─ 消息记录
                  ├─ 发送/等待
                  └─ 失败重试
```

导航必须使用统一路由栈，而不是用越来越长的字符串联合类型控制页面。

建议的系统路由模型：

```ts
type TavernPhoneOsRoute =
    | { kind: 'home' }
    | { kind: 'app'; appId: string; path: string; params?: Record<string, string> };
```

系统提供以下语义：

- `openPhone()`：打开系统；首次进入桌面，重复打开可恢复同一会话内最近的安全路由。
- `launchApp(appId)`：从桌面进入 App 根页面。
- `pushRoute(route)`：App 内前进。
- `back()`：弹出当前路由；App 根页面继续返回时回到 OS 桌面。
- `home()`：无论位于哪个 App 页面，回到 OS 桌面。
- `closePhone()`：收起设备，但不取消已经开始的后台任务。
- Tavern 会话切换：收起 Phone OS、清空导航栈和草稿视图状态，后台任务继续绑定其发送时快照，绝不迁移到新会话。

## 6. 终态架构

### 6.1 分层

Phone OS 拆为四层：

1. **平台层**：开关、呈现模式、路由栈、App 注册表、系统级返回与生命周期。
2. **系统壳层**：设备框、状态区、桌面、App 舞台、系统导航和转场。
3. **App 层**：信息、未来地图/任务/图鉴等独立 App；App 不拥有系统壳。
4. **领域层**：通讯持久化、剧情锚定、模型请求、回滚与档案；不依赖具体 UI。

### 6.3 App 注册契约

每款 App 通过注册表接入：

```ts
interface TavernPhoneAppDefinition {
    id: string;
    name: string;
    shortName: string;
    icon: string;
    accent: string;
    rootPath: string;
    order: number;
    component: Component;
    badge?: Readonly<Ref<number>>;
    isAvailable?: Readonly<Ref<boolean>>;
    onActivate?: () => void | Promise<void>;
    onDeactivate?: () => void | Promise<void>;
}
```

- OS 控制器由外部注入定义列表，不导入任何具体 App、组件或业务常量。
- OS 桌面统一读取定义中的展示信息和响应式徽标，不为信息、地图等 App 写特殊判断。
- App 可用性由响应式 `isAvailable` 驱动；能力关闭时入口和失效路由同时退出，不保留灰色假 App。
- App 舞台只通过动态组件渲染当前定义，不维护第二份 `appId → component` 分支表。
- App 的准备和释放动作进入 `onActivate/onDeactivate`，不散落在组件挂载和系统开关中。
- 注册表拒绝空 ID、非法根路由和重复 App ID，并按 `order` 生成冻结的确定性列表。
- 未来地图 App 通过薄桥接读取现有地图能力，不把地图领域逻辑搬进 Phone OS。
- 不支持的 App 不显示，不放灰色假入口。

## 7. 双端呈现契约

### 7.1 桌面端：一部真实存在的设备

- 设备最大尺寸受 Tavern 可视区域约束，保持稳定纵横比。
- 背景遮罩负责聚焦，不吞掉外部滚动状态。
- 点击遮罩、点击具有至少 44px 热区的电源控制或执行系统关闭动作可以收起手机。
- Escape 按“App 内返回 → OS 桌面 → 收起手机”的顺序工作。
- 机身装饰不抢占交互层，不允许再次出现 `4px × 90px` 这种看得见却点不中的控制。
- 设备阴影和玻璃高光在低性能环境可自动降级。

### 7.2 移动端：全屏系统，而不是手机套手机

- Phone OS 占满 Tavern 当前可用视口，移除外部设备边框、硬件侧键、假摄像头/灵动岛和假 Home 条。
- 使用 `100dvh` 与 `visualViewport` 协同处理软键盘，不依赖固定视口高度。
- 顶部和底部遵守 `safe-area-inset-*`。
- 系统关闭、App 返回和回到桌面是三个不同动作，图标、位置和无障碍名称必须明确。
- 对话输入框在键盘弹出后保持可见；消息列表只滚动自身，不推动 Tavern 背景。
- 触摸目标最小 44px，关键发送按钮建议达到 48px。

### 7.3 响应式判断

呈现模式不能只看 CSS。控制器/viewport helper 需要提供稳定的 `desktop-device | mobile-fullscreen` 语义，用于：

- 决定关闭与导航控件的位置。
- 决定转场和遮罩行为。
- 响应横竖屏与 `visualViewport` 变化。
- 在不复制 App 组件的前提下提供双端原生体验。

## 8. 系统壳体验标准

### 8.1 OS 桌面

- 显示“小白 OS”身份、当前会话的低调环境视觉和真实可用的 App 图标。
- 第一版只出现「信息」。App 图标应有清晰按压、聚焦和启动反馈。
- 未读徽标来源于真实 App 状态；没有未读时不显示空徽标。
- 不展示现实时间、假日期、假天气、假运营商或假通知。
- 空桌面仍需呈现为完整系统，不应像单个按钮被放在渐变背景上。

### 8.2 系统状态区

- 左侧保留“小白”品牌或会话归属提示。
- 信号、电量仅作为稳定的系统语汇时可以保留，不生成会随现实变化的假状态。
- 系统关闭动作必须可发现、可聚焦并具有清晰名称。
- 桌面端可有硬件细节；移动端只保留必要的系统信息与操作。

### 8.3 系统导航

- App 内返回只影响 App 路由。
- Home 返回 OS 桌面，不关闭 Phone OS。
- Close 收起 Phone OS，不取消后台生成。
- 不保留无交互的 Home 指示条；如果出现，它就必须绑定真实 Home 行为并有完整触控热区。

## 9. 第一款 App：「信息」

### 9.1 会话列表

- 顶部明确显示 App 名称，不把“小白 OS”当作列表装饰文案重复出现。
- 搜索必须是真实 `<input type="search">`：即时过滤联系人名称和已有消息文本。
- 搜索清空、无结果和输入法组合状态要正确。
- 每行显示头像、联系人名、真实最后消息摘要、发送/失败/未回复状态和未读徽标。
- 不显示现实时间；未来若领域层获得模型明确输出的剧情时间，才允许显示可选的剧情时间标签。
- 整行可点，触控热区连续，不让箭头成为唯一入口。

### 9.2 添加联系人

- 入口只在存在候选联系人时可用；不可用状态需要解释，而不是只有灰色按钮。
- 当前角色与人物记忆候选保持来源语义，但面向玩家使用自然文案。
- 添加完成后直接进入真实会话，不插入额外成功弹窗。
- 联系人空态、候选空态和重复联系人均有明确结果。

### 9.3 对话页

- 顶部返回会话列表，展示联系人身份和当前通讯状态。
- 消息列表在打开、发送完成和重试完成后保持可靠锚点；用户正在阅读旧消息时不强制跳到底部。
- 用户消息即时出现；等待模型期间显示克制且可访问的输入状态。
- `silent`、`unavailable`、`failed` 是三种不同状态，不用同一句模糊文案覆盖。
- 失败消息拥有明确的重试按钮/动作，不把整颗气泡伪装成普通按钮。
- 重试旧消息时沿用既有正确语义：移动到当前线程末尾、重新锚定当前剧情楼层、不覆盖后续消息。
- 输入框自动增高但有上限；Enter 发送、Shift+Enter 换行，并正确处理输入法组合。
- 发送按钮的禁用原因可被用户理解，不能只改变透明度。

### 9.4 后台生成

- 用户提交后立刻锁定发送任务的 `sessionId`、剧情上下文、模型配置、联系人和线程。
- 收起 Phone OS 后生成继续。
- 重新打开时恢复正确线程的 pending/完成/失败状态。
- 切换 Tavern 会话不改变正在执行任务的归属；新会话不得看到旧会话的等待状态。
- OS 导航只改变视图，不拥有或取消领域任务。

## 10. 时间与剧情真实性政策

- Phone OS 不读取或展示电脑现实时间。
- 模型 prompt 不注入现实发送时间、`sent_at` 或本地时区。
- UI 不根据 `createdAt` 格式化“今天”“昨天”或时分。
- `createdAt/updatedAt` 继续作为内部排序和事务字段，不承担剧情语义。
- 若未来需要剧情时间，必须由剧情上下文或模型以独立、可选、可修正的领域字段提供。
- 缺少可靠剧情时间时，UI 留白，而不是猜测。

## 11. 状态、持久化与生命周期

### 11.1 持久化状态

- 联系人、线程、消息、通讯快照继续存放在现有通讯领域表。
- 通讯状态继续参与剧情楼层回滚、会话分支、角色档案备份/恢复和会话删除。
- pending 数据在异常恢复、分支或档案恢复后必须转为可理解的失败状态，不能永久悬挂。

### 11.2 临时 UI 状态

- OS 开关、路由栈、搜索词、滚动位置和输入框焦点属于 UI 状态。
- 消息草稿至少按 `sessionId + threadId` 隔离；是否持久化到 IndexedDB 由实施阶段根据数据价值决定，但不得跨线程串用。
- Tavern 会话切换后不得沿用上一会话的 OS 路由或搜索结果。

### 11.3 未读语义

- 当前用户正在查看并且窗口可见的线程，在收到回复后可直接标记已读。
- Phone OS 收起、位于桌面或查看其他线程时，真实回复增加未读数。
- `silent` 和 `unavailable` 不伪造联系人回复气泡，也不产生普通回复型未读。
- 未读计数由领域状态驱动，不能只存在于组件内。

## 12. 可访问性与输入契约

- 所有图标按钮拥有准确的中文 `aria-label`。
- Dialog 打开后焦点进入 OS；关闭后焦点返回原手机入口。
- 键盘可完成：打开 App、列表导航、返回、Home、关闭、搜索、输入、发送和重试。
- 焦点环在浅色与深色界面均清晰，不使用 `outline: none` 隐藏。
- 状态变化通过合适的 `aria-live` 区域提示，但不能重复朗读整段消息列表。
- 颜色不是发送失败、未读或禁用的唯一表达方式。
- 文本在 200% 缩放下保持可操作，核心控件不重叠。

## 13. 性能与实现约束

- Phone OS 关闭时不挂载完整 App DOM。
- App 页面按需挂载；未来地图等重 App 必须懒加载。
- 动画优先使用 `transform` 与 `opacity`，避免大面积持续模糊和布局抖动。
- 消息列表增长后应保留窗口化/分页的升级空间，不在渲染阶段反复扫描所有线程消息。
- `visualViewport`、resize 和滚动监听必须节流，并在卸载时清理。
- OS 样式使用独立 token，避免继续把所有规则堆入单个 `phone.css`。
- 领域模块不得依赖 Vue 组件或 DOM。

## 15. 最终完成定义

以下条件必须全部满足，Phone OS 首版才算完成：

1. 用户第一次打开就能理解桌面、App、返回、Home 和关闭的关系。
2. 桌面端具有设备感，移动端不存在手机套手机。
3. 所有看起来可操作的元素都真的可操作；所有关键动作都有足够热区和反馈。
4. 信息 App 的搜索、联系人、会话、发送、等待、失败和重试形成完整闭环。
5. 关闭 Phone OS 或切换其页面不会取消、迁移或串联后台生成。
6. 切换 Tavern 会话不会泄漏联系人、草稿、消息、路由或状态。
7. 不展示任何现实系统时间，也不伪造剧情时间。
8. 未来新增地图 App 不需要修改 OS 核心导航和壳组件。
9. 双端真实浏览器体验通过，没有严重滚动、键盘、焦点、遮挡或误触问题。
10. 全量测试、Lint、构建和 diff 检查通过，工作区不包含旧 UI 兼容残枝。

## 17. 开发纪律

- 先完成平台边界，再做视觉细节；但每个阶段交付的界面都必须是可用的，不留假控件。
- 测试线不为本次之前的旧 Phone UI 写兼容层；冲突时直接清理旧结构。
- 不以大构建成功替代真实交互验证。
- 每个阶段完成后执行内部自查并继续推进，不要求主人逐阶段盯场。
- 只有遇到会改变产品方向、需要新外部能力或无法从代码确认的高风险决策时，才暂停请求主人选择。
- 首次集中体验应发生在 Phase 6 完成之后，而不是把半成品交给主人帮忙找基础问题。
