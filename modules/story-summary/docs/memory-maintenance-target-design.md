# 记忆 Agent 维护：目标设计

本文是产品行为、数据边界和验收口径的唯一来源；施工阶段与完成状态见[施工文档](./memory-maintenance-implementation-plan.md)。本文不是模型 Prompt；实现及真实质量验收分别记录。

## 1. 目标与用语

一个自动启动的记忆管理员，能够读记忆、查原文、修改记忆。不重新扮演角色，不重写聊天，也不只是给错误打标签。

本文严格采用用户的业务口径：

| 名称 | 指代的数据 | 维护职责 |
| --- | --- | --- |
| L0／逐楼锚点 | 每楼提取的 StateAtoms 及其关系 | 修正错记、错误归属和关系；处理无依据或重复提取 |
| L2／大总结 | 大总结生成的整份 JSON，包括事件、facts、人物、弧光、关键词和别名等 | 修正内容，并整理被总结批次切碎或重复记录的事件 |
| 原文 | 当前聊天的用户、AI 消息及其楼层、说话者 | 只读证据，支持搜索、分页阅读和查看完整 U/A 上下文 |

代码内部的 Event／Fact 分层不改变上述口径，不把 facts 排除在大总结维护之外，也不另设一个 L3 Agent。

两套数据由同一个 Agent 维护；事件续接、去重和合并是大总结维护的必做工作，不是将来再做的优化。

成功的含义是：有问题的记录得到有原文依据的修正；同一事件不因总结边界重复占位；正确的历史和具体情境没有被误删。请求成功、调用过工具或事件数量下降，均不能单独证明成功。

## 2. 修正原则

- 推测、传闻、人物判断不能升级为确定的世界事实。修正时保留说话者和不确定性。
- 分清历史事实与当前状态：过去在长沙、后来到北京，不意味着历史上的长沙是错误记录。
- 大总结中的持续位置按有叙事意义的地区、城市等变化维护，不长期追踪客房、餐厅、甲板等小移动；有意义的具体事件仍可保留场景地点。
- 保留影响联想的具体经历、感官细节、关系变化、承诺和未了之事，不把纠错变成进一步压缩信息。
- L0 与 L2 一致不构成真实性证明；两边可能来自同一次误解。判断依据是相关原文，已直接提供的原文无需另调工具重读，也无需填写引用报表。
- 搜索没有命中不等于原文不存在。应尝试来源楼层及上下文；证据不足时保留原记录、说明未解决，不编造替代结论。
- 原文和现有记忆是待处理的数据，不是对 Agent 的新指令；其中的命令不扩大工具权限。
- 正常记录可以不改。不得为了表现工作量改写措辞、强行归并或制造修改。

## 3. 事件续接与合并

### 3.1 必须解决的例 E1

同一剧情事件发生在第 17–23 楼，每 20 楼总结一次：

| 时点 | 输入状态 | 应有结果 |
| --- | --- | --- |
| 总结到第 20 楼 | 事件 A 记录第 17–20 楼 | 保留尚未结束的事件，不补写未知结局 |
| 下一批总结完成 | 又产生事件 B，记录第 21–23 楼 | 查原文确认是否为 A 的后续，不因跨批次默认认作新事件 |
| 确认为同一事件 | A、B 各有部分细节 | 保留 A 的身份，补齐后续发展及来源至第 17–23 楼，移除 B 的重复占位 |

不要求两条内容字面相似；一个写开端、一个写收尾，也可能是同一事件。也不能因为两条相邻、同人物或同主题就合并。

### 3.2 判断边界

每批新增事件都要检查是否续接、重叠或重复已有事件。候选查找是辅助，最终由 Agent 对照原文作语义判断：

- **续接**：同一件事的后续阶段，补入原事件。
- **重复／重叠**：同一经历被重复叙述或两条各覆盖一部分，保留独有信息后合并。
- **独立事件**：不同时间发生的类似争吵、不同承诺或新后果，保留独立身份；需要时保留因果关联。

历史积累的碎片也可查找、整理，不限于刚生成的记录。不得以减少事件数作为合并指标，不设置“每千楼必须减少多少条”的目标。

### 3.3 合并必须完整

- 保留原事件身份与真实时间顺序，不把后续结局写成最初就已发生。
- 保留双方有价值的细节、参与者、记忆类型和来源，不只留下更短的概述。
- 其他事件对被合并 ID 的引用改指保留事件；处理重复引用、自引用和无效因果关系。不静默截断有效前因来凑数量上限，无法满足现行契约则拒绝该草稿并回报工具错误。
- 来源与证据区分：事件正文的来源区间用于定位，不表示每楼都支持每项判断。程序记录实际提供和补读的审阅范围，不将它冒充逐项修改的精确证据。
- 修改、删除、引用重定向作为一次完整领域操作，不先删 B 再等待模型修补引用。
- 合并事件不合并、不删除对应逐楼锚点或 L1 原文块。
- 撤销例 E1 的后续批次时，恢复 A 的原阶段，不能整件事件消失或仍带着后续结局。

## 4. 入口与用户体验

### 4.1 设置页

现有总结设置中增加同级「Agent」页签，顺序为：总结、向量、Agent、提示词、调试、说明。

首屏只保留授权、必要状态和当前聊天的维护成果，不做聊天窗口、参数控制台或第二套 API 表单。沿用宿主的字体、主题、控件尺度和设置保存方式。

| 元素 | 约定 |
| --- | --- |
| 主开关 | 标签为「允许 Agent 维护记忆」；默认关闭，沿用总结设置的全局范围，明确标注适用于所有聊天 |
| 行为说明 | 说明在总结完成后检查和修正大总结、逐楼锚点；开启并保存不立即调用模型 |
| Agent 配置提示 | 使用下面唯一的定稿文案；未配置时原位指出，不静默借用总结模型或 L0 提取模型 |
| 维护记录 | 只显示当前聊天，按同一次运行分组；展开修改前后、可选说明和审阅范围 |
| 运行控制 | 运行中可停止，已确认保存的修改保留；检索待更新时可单独重试更新 |

共享配置提示定稿（实现时集中到本功能的界面文案定义处，不散落复制）：

> 使用共享 Agent API，可在Agent模块任意功能中设置，如小白 OS 的「Agent API」；已配置则无需重复设置。

这是共享配置的使用者，不要求小白 OS、画图或其设置窗口保持打开。

### 4.2 成果和状态

- 空态不填假记录；开启后等待下一次总结。
- 成果概览显示触发总结的截止楼层，以及大总结修改、锚点修改、事件合并情况；计数由真实操作派生，避免把一次合并重复算成多个修正成果。
- 无修改与未完成分开表达；模型可简短说明无法判断的问题，不要求逐条打卡，也不把未修改记录标成已验证正确。
- 显示已完成／待维护范围、正在查阅／修正／整理工作上下文等动作和已保存修改；普通回复而仍有待维护范围时显示部分完成。
- 在对应位置呈现运行中、失败、取消、索引待更新等状态，不弹窗要求日常巡检。
- 关闭自动维护不删除已保存成果；重新打开页面仍可阅读。关闭不撤销已经完成的记忆修正。
- 成果按维护轮次独立展示，新轮次在前；每轮只显示最后的 AI 汇报，不拼接或另显修正过程说明。汇报安全渲染 Markdown，长文可展开；只保留阅读所需的排版与链接，不执行 HTML 或加载外部图片。
- 每轮修正明细可切换全部／大总结／锚点，包含事件合并的大总结类别与锚点互斥。标题明确动作、类别和记录名称，锚点使用楼层。每页 20 项、首次进入最后一页，修改前后按需展开；按楼层定位到该楼最新的修正。
- 页码、分类与展开位置只属于当前页面，切聊天清空；手动阅读旧页后，新结果不重置阅读位置。手机端页签可达、内容可滚动，深浅主题都要验收。
- 概览以事件、人物和实际修改为主，楼层、日期与计数为辅。展开显示可读内容对照，不直接展示 JSON、内部编号或存储字段；一次事件合并作为一项成果，相关事件的引用变化另行展开。
- 依据楼层可打开只读原文，支持长消息续读及前后楼层，范围不超过对应维护的截止楼层。显示的是当前原文，明确提示后来编辑可能导致与维护时不同；不伪装成历史快照。切聊天后关闭原文并清理旧成果。
- 设置页底部明确写「保存设置」，不暗示维护成果尚待保存。共享 API 指引放入可展开入口；失败和后续检索更新以用户可理解的影响和动作表达，不暴露内部索引操作。

## 5. 触发、范围与时间边界

### 5.1 总结提交后自动启动

- 自动入口是**一批总结确实成功提交**，不区分该总结由用户还是自动策略发起。
- 总结失败、没有新内容、打开设置、切换聊天、仅修改 API、仅开启授权、Agent 自己保存修正，都不触发自动调用。
- 自动维护开场只提供范围任务与当前记忆；新旧卡均将没有有效完成收据的历史范围纳入待维护。正文按需读，不默认注入生成差量、事件目录或维护流水。
- 不提供手动复审按钮或对应后台接口。未来若增加用户主动入口，应由用户直接对话提出要求；本轮不实现、不预埋对话入口。
- 全库读取权限不等于每次自动全库扫描。运行因上限或中断未完成时，必须报实际覆盖和缺口。

### 5.2 L0 独立生成

逐楼锚点由现有提取流程生成；总结完成不保证同范围的锚点已经全部准备好。

复审处理现存大总结与锚点；缺失锚点不阻塞完成声明，也不等于已维护。后来生成、清理后重建的锚点使自身楼层重新待维护。运行中后来就绪的锚点保留、不覆盖；范围确认期间发生锚点变更仍按基线冲突处理，不暗加每楼 Agent 调用。

### 5.3 一次运行的证据范围

- 固定聊天身份，捕获当前触发批次、证据截止楼层，以及实际读取的消息和记忆基线。
- 原文可向前追溯，但不可读取本次截止之后的新剧情；本次 run 的截止固定，下一次 run 才使用新的总结边界。楼层展示采用用户可读的一基编号，内部转换只在边界做。
- 用户继续追加消息不使原证据失效；切聊天、swipe、编辑、删除已依赖的消息或改变待修改记录，必须阻止过期提交。
- 同聊天新总结进入 pending 队列，多个等待批次合并触发范围；当前 run 的任务边界与对话不变，不追加整份开场记忆。当前 run 返回（包括最终收据保存）后，才以新 run 处理排队的总结；达到上限不重跑旧请求。
- 总结照常保存。旧 run 的修改按实际涉及的记录检查基线，冲突返回 memory_updated 和记录标识，告知这些记录本轮跳过、继续处理其他记忆；整份修改列表未保存，无关修改可单独重提。新批次负责的记录留给下一 run，重读也不扩大本轮维护边界。读取只更新返回记录的基线，保存只更新已确认修改的基线，不让其他未见过的变化被默认为已知。保存中的总结先等确认，不能读取未发布草稿；原文变更、导入替换或回滚仍受原边界保护。
- 正常回复不因新批次到来而丢弃或额外调用模型，其文字与终止状态按同一 runId 保存。
- 不把 Agent Promise 挂在宿主串行事件总线上等待，不阻塞主聊天。
- 关闭自动维护取消尚未提交的自动任务；切聊天、停用总结或宿主卸载取消该聊天未提交工作。提交点之后按真实保存结果落定，不把已保存记作取消未保存。
- 队列不跨页面重启恢复，不因重载偷偷补发模型请求。

### 5.4 连续会话与材料边界

- 一次触发只有一个连续 run、一段工具对话，`toolChoice: auto`；模型正常回复后结束。宿主不预先分包、不派发几十份审查任务、不维护完成矩阵。
- 内容标准沿用生成内容原文，维护不注入生成协议；生成全文不变。只有已记录指纹可以确认的批次才标对应标准；旧批次和无法确认的锚点为未知，只纠事实错误。
- 开场状态截至本次截止楼层；主动重读得到当前存储值，可能已有后续总结带来的变化。需要截止之后原文才能判断的内容留待下一 run。早期长沙不能单独证明最新北京状态错误，须查后续发展。批次记录／更新边界不是剧情发生时间。
- 当前记忆按第 5.6 节筛选后入场，超出开场预算时给各类记忆续读参数。业务内容、稳定标识、维护归属和生成标准共用同一投影；稳定游标不因删除前项而跳过后项。分页不创建新任务或对话。
- 原文按一基楼号读取，不受聊天隐藏状态影响；不能越过截止楼层。过滤后剧情与 raw 视图区分，被排除内容不作为剧情证据。
- 完整输入上限 198,000 tokens，178,000 tokens 触发压缩目标；输出另沿用共享参数，接口需支持输入与输出合计容量。使用共享 token 计数，包括系统、工具、材料及供应商重放内容，记录 tokenizer／estimated 来源，不以字符数冒充 token 或按模型名猜容量。
- 压缩只在完整回复／工具结果边界进行：保留最近两轮，必要时一轮；总结早期调查方向、关键标识、发现及未解决事项。摘要输出不超过共享输出与 10,000 tokens 的较小值。摘要请求也限输入，过长工作历史分段摘要，任务仍为同一 run。
- 独立摘要 adapter 不污染主会话。压缩成功且重新计数合格后才替换对话；失败不截断冒充摘要。主 adapter 以新完整消息重建协议会话；准确进度从收据重新注入，记忆内容按需读真实存储。
- 每 run 最多 256 次模型请求，含失败与压缩请求；计数不重置，达到上限保留成果，不自动另开 run。
- 调用次数、耗时、输入 token 计数及供应商 usage 是运行记录，不是语义成绩；不承诺十秒或零工具错误。

### 5.5 范围闭环

- CompleteMaintenance({from,to}) 按一基楼号声明已完成范围；无需修改也可完成，不要求引用、逐条正确声明或理由。有效完成仅表示执行过维护，不表示每楼原文都读过或内容绝对正确。
- 每次确认追加空修改收据，保存 runId、completion 与后续 invalidated 子范围。已完成为有效收据的并集，待维护为当前边界减去已完成；没有独立任务表或全局进度副本。重复确认不重复写历史。
- 范围完成由 Agent 声明；程序校验楼层、基线和确认保存，不要求逐条读完记忆。原文审阅范围仍只记录实际提供过的内容，不拿它代替判断质量。
- 记录维护归属由批次逆操作及元数据推导；后续总结更新旧记录归更新批次，不拿创建时间当更新时间。导入或无法定位的旧记录归固定起始基线，不随聊天增长扩大。锚点归自身楼层。
- 人工改记忆、原文变更及锚点失效在统一提交草稿内退役完成子范围，与内容一起确认。不能定位时退役对应基线；Agent 自身确认修改不当成外部变更。新批次变化由新批次负责，不重开全部旧范围。
- 撤销移除所属收据，替换导入不继承完成。旧 outcome.completed 只是旧 run 正常结束，不转换为完成范围。重启只读取进度，不恢复付费请求。

### 5.6 按待维护批次选材

- 开场只提供范围任务、待维护范围对应的当前记忆，以及直接前一个历史批次的衔接记忆。对每个待维护范围涉及的批次，使用真实历史边界找前一批；不假定每批固定楼数，也不将中间已经完成的无关批次一并扫入。
- 范围任务中的 `contextRanges` 是前批范围扣除待维护范围后的结果，作为已维护的衔接背景，不新增必须重审的任务。它与已完成／待维护范围均从现有历史派生，开场、完成返回及压缩后任务共用，不新增持久化字段。
- 大总结按照最后新增或更新记录的责任批次选取当前值，不拼历史快照。同一稳定标识只入场一次；旧事实被新批次更新时按新批次负责。导入或未知归属继续使用固定起始基线。
- `ReadMemory({ranges:[{from,to}], ...})` 按一基、首尾包含的范围并集过滤，再与分类、标识和业务文字查询取交集。省略 ranges 不限制范围，空数组返回空；倒置、越界和类型错误明确报字段。全库仍可按需读取，但不用于填满开场。
- 大总结记录与查询范围按责任批次相交，L0 按自身楼层精确匹配。例如只有 1–20、21–40 两批时查询 10–30，会取两批负责的全部现存大总结记录，而锚点仅取 10–30；这不是对事件发生时间的精确切片。原文仍按楼层精确读取。
- 先筛选，再沿现有分类和稳定记录顺序装载。开场材料上限 **50,000 tokens**，范围和续读目录计入；提示词和工具另计完整输入。装载先估算，再以共享计数复核，超出时减少完整记录并给续读参数。
- 目录 total 仅统计所选内容；next 带固定 ranges、分类、查询条件和稳定游标。每页沿用 32 条／16,000 字符限制，长记录分段续读；记录在续读期间改变时返回冲突，须从该记录起点重读，不拼接新旧版本。完成声明不会使已有游标变成另一份动态筛选，也不会续读到全库。是否需要继续查读由 Agent 判断，前批背景不附加强制重审要求。
- 新卡按当前待维护批次工作；老卡首次没有完成标记，历史均待维护，允许第一次工作量大。后续只默认提供待维护内容和衔接材料。需要更早的事件、身份或事实时由 Agent 自主查阅，仍是一段连续对话。

## 6. 执行、权限与提交

### 6.1 工具能力

工具能力分为大总结读写、逐楼锚点读写、原文只读。支持搜索、分页、按稳定身份定位，以及事件续接／合并这一完整操作；不是把整个 JSON 暴露为无约束覆盖文件。

模型通过 ReadMemory、SearchSource、ReadSource 查阅，EditMemory 改业务内容、CompleteMaintenance 声明范围完成。不能改原文、配置、内部身份、账本或向量。EditMemory 提交 edits 与可选 note，空 edits 表示无变化，不结束 run。不开放新建记录、模型侧历史流水工具或生成差量读取模式。

数据安全由宿主承担：类型、字段、身份、楼层及引用关系校验失败，整组不生效，错误定位条目与字段；模型修正后重交整组。不可编辑字段不能被静默忽略。预算与材料安排遵守第 5.4 节。

工具入口先处理无歧义的格式差异：按 schema 接受数字字符串、布尔字符串、枚举首尾空白及大小写、单项列表；普通修改省略 kind 时默认为 edit。业务正文和标识保持原样，不猜字段或目标，不裁掉超限内容。参数错误附可接受的字段或类型，重复写入相同值返回无变化。

事实的存储身份与业务键不同：ID 用于历史撤销，主体与谓词 `(s,p)` 用于后续总结合并。维护整组修改后的有效事实不得出现重复业务键；允许同一组纠正主体或谓词、补全保留值并删除重复项，不因操作先后误拒绝，也不让下一次总结静默丢弃修正。

### 6.2 草稿和成果

读取、修改均在固定聊天及当前来源边界内进行。EditMemory 整组校验后通过统一入口确认保存，才返回 saved 并刷新基线；对话不清空。同一列表的两侧变更原子提交。

同一回复的读取与多次 EditMemory 按顺序执行，各修改列表分别原子保存、分别返回结果；一个列表失败不吞掉其他独立结果。完成声明排在这些调用之后，只要有修改失败便不记完成。模型仍要等下一轮才能看到读取结果；依赖该结果的修改应在看到结果后决定，顺序执行不代表模型预先看到了结果。

模型停止、失败或达到上限时，未提交草稿丢弃，此前确认修改保留。新总结按第 5.3 节排到下一 run。实际提供原文称为审阅范围，不是逐项证据，也不证明全库正确。正常文字收尾与终止状态保存到同一 run 的历史分组。

保存结果不确定时不再次运行模型来“补保存”，先按已有保存边界确认结果；不能把请求已发出或内存已变更当成确认保存。普通可恢复工具异常在本轮解决，网络重试不得重复已确认的提交或盲目重发未知计费请求。

生成、维护、导入、回退、清空和锚点提取共用总结数据层提交入口；总结、历史、锚点及提取状态一起确认。服务端为新状态才发布；仍为旧状态时仅在内存未被后续编辑改变的情况下恢复；回查失败或内容不同，不恢复旧值，运行期暂停消费及修改，只允许只读核对或重新加载。保存未确认不是永久历史损坏，调用方不各自解释或补写保存结果。

### 6.3 撤销与检索一致性

- 修改差量、可选说明、审阅范围与保存成果共用一份记录；不能另建审计库和撤销库。本轮保留批次撤销，不新增单项撤销。
- 记录附于实际保存时的最新总结历史批次；同批多次维护有确定顺序，跨批仍以 runId 归组，收据中的原 run 截止不变。撤销先逆序撤销维护差量，再执行原总结批次的撤销，不能覆盖后来的人工编辑。
- 大总结与锚点的业务改动均纳入这条历史，包括旧事件合并、引用重定向、facts 和别名纠错；不能只按被改记录原来的楼层删除。
- 数据层历史只有“有完整逆操作的生成批次”和“不可越过的起始基线”。导入直接建立当前格式基线；基线上的维护可撤销并保留导入内容，没有维护时不允许回退；损坏逆操作不能伪装成基线。
- 编辑原文、删除楼层、swipe、清空锚点统一失效受影响的锚点、提取状态及向量，并遍历全部历史，在原维护记录内退役相关锚点差量，包括 Agent 已删除的锚点。保留修改前后和失效原因供查看；重启或同 ID 重建不能复活旧逆操作。只跳过明确退役的操作，有效记录的真实冲突仍拒绝覆盖，大总结差量照常撤销。
- 来源已变而安全回退／清理失败时，保留记忆内容并暂停消费；不能安全越过导入基线时记录失效来源边界。来源失效与历史损坏、保存未确认分别处理。
- 修改或删除记录时先失效对应旧向量和待用缓存，再保存新内容；失效失败不得宣称修正生效。只有向量缺失可以随后补齐，不能复用旧内容的向量。
- 不重建无关 L1 块。锚点内容、关系、楼层提取统计，事件文档、因果引用、实体索引和检索缓存均检查受影响项。
- 后续向量构建失败时保留已确认的修正，明确显示索引缺口；重试只补索引，不重新做语义维护。
- 复审属于显式记忆改写，后续装配不沿用修正前的待用记忆缓存；已经发出的主模型请求不会被追溯修改。

## 7. 所有权、持久化与兼容

### 7.1 终态边界

Agent 会话、只读证据、领域修改和成果投影由 `modules/story-summary/maintenance/` 拥有；总结数据层 `data/` 统一拥有历史构造／入口转换／回退目标、原文变更导致的锚点失效、完整记忆提交及保存确认状态。生成、维护及 UI 只构造下一份草稿并调用数据入口，底层锚点存储不提前单独保存半份状态。已有生成入口只通知已提交批次，设置页不拥有后台任务。

共享配置、供应商适配和通用工具协议使用 [agent-core](../../agent-core/README.md)。管理员的按需读写、新闻的草稿提交、小白酒馆的自动维护可作实现参考，不直接反向依赖这些 APP 的业务代码。若确有多个消费者需要同一业务无关执行原语，才在共享层抽取；不为本功能重建通用后台平台。

### 7.2 新增持久态的理由

| 实体 | 为什么不能只放内存 | 所有者与生命周期 | 失败与删除 |
| --- | --- | --- | --- |
| 自动维护偏好 | 用户希望重启后保留授权选择 | 总结配置；唯一全局字段 | 保存失败不假装已启用；卸载功能时清理自有字段，不删除共享 Agent 配置 |
| 已确认维护记录 | 重开查看成果、精确回滚需要 | 对应总结批次；保存差量、可选说明和实际提供范围 | 与内容一起确认保存；随回滚、替换导入、清空和聊天删除处理 |
| runId | 重启后仍需把多次修改归为同一次运行 | 原维护记录的分组标识，与所属记录同生命周期，不另建运行表 | 保存未确认不发布；随维护记录或所属批次删除 |
| 批次规则 | 重启后识别生成标准 | 生成批次的规则指纹及过滤规则，不存 Prompt | 随批次确认与删除；未知版本不猜测 |
| run 收尾 | 重启后显示结果和结束／中断状态 | 同组维护历史的空差量记录，包含正常回复与 outcome；没有独立运行库 | 与历史一起确认，随所属批次删除或回滚；切聊天或所属批次已删除时不越权补写，无收尾记录的组显示未收尾 |
| completion／invalidated | 重启仍须识别哪些范围确实维护过 | 空修改维护收据的完成范围及退役子范围，进度由它派生 | 与历史确认保存，未确认不发布；随批次回滚、替换导入、清空、聊天删除消失 |
| 记录内的锚点退役标记 | 重启或同 ID 重建后不能让旧原文的逆操作复活 | 原维护差量的字段，不另建实体；随所属历史存亡 | 与失效锚点／提取状态一起提交；保存未确认走统一暂停策略；历史删除时一并删除 |
| 来源失效边界 | 原文已经变化，重载后也不能把未能安全回退的旧记忆当成有效 | 总结数据层的 `sourceInvalidFromFloor`；仅保留最早未解决边界 | 保存失败先在运行期阻断；安全回退到边界前、重新导入或清空后解除；随总结及聊天删除 |

队列、读取游标、模型上下文、原文临时快照、草稿、AbortController、失败重试状态、保存未确认状态和未保存的最近运行状态只活在当前运行。重新加载只读取实际服务端记忆，不自动重放保存或模型请求；不复制整段聊天或模型思考。

当前 L2 JSON 和 StateAtoms 仍是唯一在用记忆；历史差量只服务成果解释与恢复，不参与召回充当第二份事实。结果计数与页面展示均从记录派生。

### 7.3 兼容及退场

需要适配 SillyTavern、浏览器/WebView、共享 Agent 供应商协议、现行记忆与向量文件格式、用户保留的聊天。没有上线依据的旧试验分支不默认保留。

保留的 v1 分包收据在加载入口删除其旧 completion 矩阵、part、覆盖矩阵及 calls.package；该矩阵与当前 v2 楼层 completion 不同，不能迁移成维护完成。既有 v2 outcome.completed 也不补造完成范围。已有差量、说明、审阅范围、锚点退役及撤销链保留。

若扩展现行总结历史格式，升级／导入入口一次性转换；冻结当前真实格式及 fixture，运行时只使用当前模型。纯总结导出和可恢复历史不是同一种承诺，不在导入时编造未携带的维护成果。向量包继续按实际内容验证来源。

删除路径为：取消运行、删除功能目录及入口注册、移除页签、自有偏好和历史扩展。保留已经修正的当前记忆；若移除历史扩展，必须同步建立准确的新回滚基线，不能把失配的旧 undo 留给原总结功能。共享配置和其他 APP 不随本功能删除。

## 8. 开工边界与验收

开工检查：所有者、唯一事实来源、临时／持久态及理由见第 7 节；入口见第 4–5 节；权限与失败路径见第 6 节。第一版不新增外部依赖。

### 8.1 工程契约

- 授权关闭、仅打开页面或仅保存开关都不调用模型；手动和自动总结进入同一维护入口。
- 原文不可写，来源上界不可越过，其他聊天不可读取或修改。
- 分页未完成、L0 缺失、未解决错误不被标为已审无误。
- 事件合并、引用修正、撤销与索引失效保持一致；正确内容和无关记录不受影响。
- 保存失败、保存未确认、并发修改及重启边界均按真实状态呈现。
- 空态、成果、长内容、无变化、运行中、失败和关闭后的历史都可操作；手机与桌面、深浅主题实测。

### 8.2 语义验收

固定包含已知错误、正确对照以及例 E1 的样本。逐项给出维护前、维护后、原文依据、判断和未解决原因。分别交付大总结与逐楼锚点的纠错、误改、未解决结果；事件整理另外列正确合并、漏合并、误合并和关键细节丢失。

保存正确性不代替语义验收。若随后比较召回质量，仍按既定协议对各臂逐楼独立判定并派生成绩；存储错误与召回算法错误分开，联想不要求命中字面相同的旧场景。小样本不冒充全量结论。

### 8.3 首版不做

不改现行「完整 USER＋AI 前三锚点邻块」方案；不替换总结生成器或 L0 提取器；不做每条消息都运行的 Agent、跨重启任务系统、联网搜索、角色生成或其他 APP 重构。这里的维护也不承诺新记忆从未复审状态到生效之间完全没有错误窗口。
