# 聊天分支的变量 2.0 状态恢复（暂缓）

## 决策与当前行为

**暂缓实现。保留当前运行行为，待识别机制、恢复时序和兼容验证足够完善后，再单独决定是否开发。** 本文记录有效的问题定义与设计约束，不表示已有可启用的修复，不授权修改酒馆本体。

酒馆创建分支时，复制截至目标楼层的消息，同时继承创建时的当前聊天变量。变量没有丢失；缺口是变量 2.0 尚未将新分支的状态恢复到所选剧情点。

| 剧情点 | 当时的钱 |
| --- | ---: |
| A：开局 | 120 |
| B：第一次消费后 | 100 |
| C：第二次消费后，也是当前聊天末尾 | 60 |

- 从当前 C 回复开分支，继承 60 符合当前状态，无需额外历史恢复。
- 从旧楼 B 开分支，消息截至 B，但变量仍继承 60。只有要求“分支回到 B 当时的状态”时，才需要恢复为 100。
- 从同一楼的另一条 swipe 开分支，还要考虑所选回复与当前回复的状态操作不同，不能只检查消息数量。

这是小白X的历史状态适配缺口，不是酒馆丢失变量或复制消息错误。现有回滚能力并不等于分支创建路径已接入回滚。

## 已确认的宿主行为

以下对应已核查的本地版本源码；未来宿主版本需重新确认。

| 行为 | SillyTavern 1.14 / 1.18 | SillyTavern 1.19 |
| --- | --- | --- |
| 分支消息截止到目标楼层 | 是 | 是 |
| 分支专用、可等待的保存前扩展事件 | 未提供 | 未提供 |
| 分支继承父聊天的 `integrity` | 是 | 否：原生分支生成新 UUID |
| 原生检查点生成新 `integrity` | 否 | 是 |

`CHAT_CREATED` 用于空聊天生成首条消息，不能当作分支创建通知。`CHAT_CHANGED` 表示打开或切换聊天，普通重开旧分支也会触发，不能无条件回滚。

分支和检查点都可能带有长期保存的 `main_chat`，它不是“这次刚创建”的一次性信号。原生 `createBranch` 还可以被第三方单独调用而不立即打开分支；加载时识别不等于保存前处理，也不覆盖第三方绕过原生函数自行写文件的行为。

1.14 的群聊元数据与 1.18 / 1.19 的存储位置不同，不可假定一个保存请求就是所有版本共用的接入点。仍须维持项目对 1.14 和 1.18 的兼容，不能因存在 1.19 的新行为而改坏旧版本。

## 1.19 身份机制的验证结论

候选办法：状态日志记录它所属聊天的 `integrity`。原聊天的 ID 为 A、日志归属也为 A；原生分支得到 ID B，但复制来的日志归属仍为 A，因此能识别“日志来自另一份聊天”。成功完成分支状态恢复后，再将日志归属绑定为 B。

**当前变量 2.0 日志没有这个归属字段。它是候选设计，不是现有能力。** 仅升级到酒馆 1.19 不会自动修复历史状态。

在隔离的原生 1.19 单聊环境中，使用测试归属字段验证了：

- 历史楼层分支、末楼另一条 swipe 的同长度分支、分支再开分支：获得新 ID，复制旧归属。
- 更新测试归属后，重开、改名、正常 JSONL 导入：不会再次出现归属不匹配。
- 未更新归属的分支再次打开：仍然不匹配，证明它不是一次性的创建通知。
- 导入文件缺少 `integrity`、但保留归属字段时，酒馆补发 ID，也会产生不匹配。这不是一次原生分支创建，是直接按不匹配回滚的反例。
- 没有事先记录归属的日志，不能通过此比较判断来源。

上述验证只证明宿主对身份及复制字段的处理；测试中没有执行变量 2.0 恢复，也没有证明循环任务时序、群聊运行、单楼初始化或性能已满足交付条件。

## 以后再评估的方向

### 识别入口

- 若宿主提供正式的分支保存前接口，优先在明确的创建流程中处理目标副本。
- 1.19 可以继续研究纯插件的日志归属识别，但不能把“ID 不同”直接等同于“本次刚创建分支”。须核对来源和实际消息，区分正常派生、导入、标识缺失及未被插件接管就已继续发展的聊天。
- 不根据文件名、`main_chat`、消息长度或越界日志中的任一单项直接判定新分支。
- 缺少可靠来源的数据不擅自回滚；不能声称为未知旧数据补一个标记就已恢复历史。
- 不默认采用全局保存请求拦截，也不要求用户换用一个不能覆盖原生操作的替代按钮。

若最终采用日志归属字段，应只存在于变量 2.0 日志的元数据中，而不是每楼新增快照。它之所以可能需要持久化，是为了重启后仍能区分已经处理与继承而来的日志；与日志同生命周期、同删除路径。状态恢复和归属更新必须作为同一完整结果保存；失败不得提前改归属。插件只读取宿主的 `integrity`，不修改其完整性凭据。

### 复用恢复能力，而非新造存档

当前 [重建器](<rebuild.js>) 已将临时计算与发布分开；请求、检查点和受管根的唯一结构定义见 [恢复设计](<json-tool-design.md>)。未来分支处理应让它计算明确的目标副本和独立规则上下文，再把完整结果发布给分支，不能先修改原聊天再改回来。

- 保留原回复：恢复到目标楼层执行完毕。
- 选择其他 swipe：恢复到上一楼，再应用实际选中回复的状态操作；不能沿用该楼旧 swipe 的日志。
- 选中回复确实没有状态操作：保留上一楼状态。若状态文本或对应记录已丢失，不能把“无法恢复”冒充“本来没有变化”。
- 在裁剪日志前确定变量 2.0 管理的根变量范围；只处理这些状态及对应规则，不改未纳入管理的变量。
- 同步处理各 swipe 的请求记录和检查点，保证新分支不携带不再适用的未来记录，也不重复执行增量。

临时副本只用于内存计算，最终替换分支已有的状态数据；不嵌入父聊天，不新增每楼全量存档。

## 恢复开发前必须满足的条件

1. **数据安全**：原聊天、未纳入变量 2.0 管理的变量及现有任务保持原行为；不增加授权弹窗，不伪造删除或 swipe 事件来强行触发恢复。
2. **执行顺序**：恢复与现有初始化正确衔接，既有 `chat_changed` 任务读到应有状态且按原次数运行；不得靠禁用或跳过任务解决。单楼分支和重开不能重复执行状态增量。
3. **可靠保存**：识别、恢复和归属更新有明确的成功及失败语义；保存失败、切聊中断不留下半处理状态。宿主事件派发会记录并吞掉监听器异常，不能假定抛异常就会阻止后续保存。
4. **覆盖验证**：单聊与群聊、历史分支、其他 swipe、无状态回复、单楼与同长度分支、重开、改名、导入和缺失归属数据均有语义验证；版本限制明确，不将 1.19 的结果冒充 1.14 / 1.18 通用能力。
5. **性能验证**：复用有效检查点和已有记录，不在每次切聊天或发消息时全量重放；验证长聊天和移动环境的分支耗时、页面响应及内存，而非预先承诺不卡。

这些条件没有满足前，维持暂缓，不把候选身份机制包装成已完成的修复。
