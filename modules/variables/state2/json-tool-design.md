# 变量 2.0：请求记录与恢复设计

使用方式与返回字段见 [使用说明](<README.md>)。本文面向维护者，说明数据怎么存、怎么恢复。

## 1. 目标

- 写入入口：正文 `<state>`（文本格式或 JSON）、`LWB_StateV2.apply()`、`LWB_StateV2.applyText()`、`beginTurn()` 句柄的 `commit()`，共用同一套操作与守卫。
- 每个 swipe 在自己的 `message.extra` 中保存它的变量**请求**。换 swipe、编辑、删除时，变量由这些请求重建。
- 正文只是输入的载体。状态块执行后被正则或手动删除，记录仍在。
- 所有修改同步完成，任何时刻对外只有完整状态。
- 存储随请求量线性增长；全量状态只存在于最多两份检查点中。

## 2. 语义

### 2.1 一楼的变量结果

```
楼层 k 之后的状态 = 楼层 k-1 之后的状态 + 楼层 k 当前 swipe 的条目（按记录顺序执行）
```

条目按实际发生顺序排列：正文生成过程中的调用排在正文之前，正文处理后的调用排在正文之后，多次 continue 新增的正文各自排在发生的位置。

重建按请求重新执行并经过守卫。前文变化后，同一请求可能得到不同的修正或拒绝结果，这是"按新前文重演"的含义。

### 2.2 正文输入同步规则（B 语义）

记 `cur` 为当前正文中各状态块的指纹序列，`rec` 为本 swipe 记录中所有正文条目的指纹按顺序拼接的序列。

| 条件 | 处理 |
| --- | --- |
| `cur` 为空 | 不处理，保留记录（块被清理不等于撤销） |
| `cur` 与 `rec` 相同 | 不处理 |
| `rec` 是 `cur` 的前缀 | 只把多出的块解析为一条新正文条目，追加到条目末尾 |
| 其他 | 视为修改：删除全部正文条目，把 `cur` 全部块解析为一条正文条目，放在原第一条正文条目的位置，然后重建 |

- 正文中还有状态块时，这些块整体就是这一楼的正文输入。两块删掉一块属于修改，被删的那块会撤销；全部删光则保留记录。
- 新输入解析失败时报告错误，记录和状态保持不变。
- 指纹是块原文（去首尾空白）的短哈希，只用于比较是否相同。

### 2.3 宿主操作对应

| 操作 | 处理 |
| --- | --- |
| 正文生成完成（经现有 after-ai gate）、用户消息渲染、`MESSAGE_UPDATED` | 对该楼执行正文同步 |
| 编辑（`MESSAGE_EDITED`） | 对该楼执行正文同步；不做回滚 |
| 换到已有 swipe | 宿主已把该 swipe 的 `extra` 载入消息；该 swipe 无记录而正文有状态块时，先把正文解析为正文条目；然后重建 |
| 换 swipe 新生成 | 清除消息 `extra` 中本模块记录，然后重建；生成中的调用和生成完成后的正文写入新 swipe |
| 删除 swipe | 从事件给出的目标 swipe 读取其请求和正文，同步重建，只更新本模块的 `extra` 字段 |
| 删除消息 | 重建 |
| continue | 由正文同步的前缀规则处理 |
| 打开聊天 | 转换旧数据（如有）；扫描记录得到受管根；不重建 |

这些处理都在事件回调内同步完成。新生成的 swipe 由 `swipe_id >= swipes.length` 判断。

1.0 模式只使用 API 的执行与记录；编辑、换 swipe、删除仍由 1.0 自己的快照处理。

### 2.4 操作范式与批次边界

输入采用“操作名、路径、操作数”的命令格式。参考 [JSON Patch（RFC 6902）](https://www.rfc-editor.org/rfc/rfc6902.html#section-4) 对操作、路径和错误的显式定义，但本接口不是 JSON Patch：它保留文本执行器的下标删除倒排、批量追加、增减及规则守卫，也不承诺顺序补丁的执行方式。

- 一次提交的下标删除先执行，同一父路径内倒排，其余请求保持原序。
- 新 JSON 请求在入口做纯预检：拒绝重复下标删除、因删除导致目标移动的按下标操作、与删除数组项重叠的祖先替换/删除。按解析后的路径段比较，避免点路径与方括号别名漏检，也不把带点的单个键误当成嵌套路径。
- 同一正文条目的多个块合并后再检查；已经执行过的条目不参与下一次提交的预检。纯文本冲突对不受无关 JSON 操作影响。
- 输入被拒绝时，变量、记录、规则和旧数据均不改变。历史记录直接重放，不套用新输入检查，更不重排或改写旧请求。
- 调用方的纠错方式与具体执行顺序见 [数组批处理与返回契约](<README.md#同一批里删数组项要小心>)。

错误采用稳定标识、结构化位置与人类说明分离的形式，参考 [Problem Details（RFC 9457 §3）](https://www.rfc-editor.org/rfc/rfc9457.html#section-3) 的设计思路。本接口返回自定义 JS 结果对象，不实现该规范的 HTTP 响应格式。结果回执与通知事件是两个独立对象；操作错误、守卫修正和提交后的通知警告分别表达。

执行层复用已有路径解析和原生对象、数组操作，保持文本写法及历史请求的执行语义；不引入 Lodash，也不增加 JSON Patch 或 Problem Details 的协议适配层。根变量、路径成员和规则查找仅使用对象自身属性；`toString` 等合法名称不继承原型上的值或规则，未写入时按缺失字段处理。

## 3. 数据

### 3.1 swipe 记录

位置：`message.extra.LittleWhiteBox_state2`。写入时同时更新 `message.extra` 与 `message.swipe_info[swipe_id].extra`（存在时），两者内容相同。

```json
{
  "v": 1,
  "entries": [
    { "kind": "text", "roots": ["角色"], "blocks": ["3f9a1c2e7d84b605"], "rules": [], "ops": [{ "op": "set", "source": "text", "path": "角色", "value": { "金钱": 100, "日志": [] } }] },
    { "kind": "call", "source": "json", "roots": [], "ops": [{ "op": "inc", "source": "json", "path": "角色.金钱", "delta": -10 }] },
    { "kind": "call", "source": "text", "roots": [], "blocks": ["b71d0e4412a6c908"], "rules": [], "ops": [] }
  ]
}
```

- `kind: "text"`：一次正文输入。`blocks` 为对应状态块指纹，`rules` 为规则声明，`ops` 为解析出的请求，每条请求带来源（文本格式或 JSON）。
- `kind: "call"`：一次直接调用。`source: "json"` 来自 `apply()`；`source: "text"` 来自 `applyText()`，带 `blocks` 用于防重，可带 `rules`。
- 存的是解析后的请求：`inc` 存增量，`push` 存追加项，按值移除存要移除的值，`del` 存路径，`set` 存调用方给出的值。不存执行结果，不存状态快照。
- 记录使用执行器的内部操作名。按值移除的内部名为 `pop`；JSON 入口对外叫 `remove`，在输入校验时转换，`apply()` 返回的 `changes` 也换回 `remove`。
- 记录只整体替换，不原地修改，便于按对象缓存指纹。

### 3.2 受管根

每条记录的 `roots` 保存该条目接管的根变量，是所有权的唯一事实来源。新文本条目在入口由文本来源请求与规则声明计算；纯 JSON 调用为 `[]`。旧记录的范围按第 5 节转换，不因重放时某条原本失败的请求变得可执行而扩大。

当前受管根是所有消息当前 swipe 条目 `roots` 的并集。JSON 来源请求只能操作已受管的根，不能产生受管根；判定以该请求之前的条目及本条目已声明并生效的接管范围为准。初始化记录被删除后，留在后面的 JSON 请求在重放中失效；之后再有文本请求重新初始化该根，也不会让更早的 JSON 请求复活。

条目的接管事实随记录持久化，因为旧版失败请求是否曾纳管无法仅从请求内容还原；替换或删除条目时一并替换或删除。聊天级并集只在运行期派生，不另存一份。同一聊天替换 metadata 对象不会丢失删除前的受管范围；明确重开聊天时重新扫描。

根的初始值必须能从记录中重建，例如用文本整体赋值初始化。原生接口绕过本模块写入受管根，不会自动形成历史请求，恢复时不保证保留这些未记录的修改。检查点也只缓存请求重放的结果，不能把偶然存在的原生写入当成历史基线。

### 3.3 检查点

位置：聊天元数据 `extensions.LittleWhiteBox.stateCkptV2`。

```json
{ "v": 4, "points": [{ "floor": 2999, "digest": "…", "variables": { }, "rules": { } }] }
```

- 候选楼层：`(floor + 1) % 50 === 0`，即每满 50 条消息一个。
- 最多两份，保留不超过末楼的最高两个候选楼层。
- `variables`、`rules` 为从空状态重放楼层 0 到该楼全部记录得到的完整结果。重放结果只取决于这段前缀（见 4.4），缓存不按整段聊天的受管范围裁剪。
- `digest` 为楼层 0 到该楼各记录的有序前缀摘要：`d[k] = hash(d[k-1], hash(记录k))`。摘要不符即无效。删除、移动、编辑、换 swipe、导入引起的任何前缀变化都会使摘要不符，无需另行跟踪失效。
- 检查点是缓存，无效、缺失或版本不同时从更早位置重放，不影响正确性。有无检查点，恢复结果必须相同。

### 3.4 其他持久化数据

- 当前变量值：宿主聊天变量，不变。
- 规则表：`LWB_RULES_V2`，作为当前规则状态，不变。
- 不再使用：`stateLogV2`、`LWB_STATE_APPLIED_KEY`、检查点 v1。由旧数据转换一次性删除。

### 3.5 运行期状态

受管根集合、记录指纹缓存（以记录对象为键）、保存防抖计时器，以及当前生成轮次和待处理的生成后通知。聊天切换、模块关闭时取消未完成通知；重启后不恢复这些过程状态。

## 4. 流程

### 4.1 正文同步 `syncBody(floor)`

1. 读取该楼当前 swipe 记录和正文状态块，按 2.2 判断。
2. 追加：解析新块。若该楼是末楼，在临时变量存储上执行，准备好回执和条目后发布；否则追加条目后重建。
3. 修改：解析全部块，替换正文条目，重建。
4. 写回记录，安排保存，发出通知。

生成后的正文处理等待宿主退出生成状态并完成渲染，不在流式中途执行。消息到达、渲染完成、生成结束的重复通知合并为当前真实生成轮次的一次后处理；不以消息发送时间去重，继续生成沿用同一楼和时间戳也要处理新增内容。正文请求仍按记录防重；新一轮即使没有新增状态块，也保留宏渲染与变量事件收尾。聊天切换和模块关闭取消尚未执行的处理。

JSON 来源请求在处理时检查受管根，未受管的请求报错并不进入记录。历史楼层的准入、执行回执与落账使用该条目在重建位置上的同一次执行结果；正文替换时，被替换条目及之后的记录不能为新条目提供准入范围。无记录 swipe 的正文使用同一规则。

### 4.2 直接调用 `apply(input)`

1. 校验并复制输入，执行 2.4 的批次预检。同源 iframe 的对象按数据内容接受；拒绝访问器、循环引用、非有限数字、`undefined`、危险路径及操作定义以外的字段。输入不合法时，连旧数据转换也不启动。
2. 取得当前聊天与末楼；无聊天或无消息时返回错误。准备受管范围，必要时转换旧记录。
3. 检查受管根，未受管的请求报错。
4. 在临时变量存储上执行其余请求。
5. 把通过第 3 步的请求作为一条待提交的 `call` 条目，并构造与执行对象深隔离的完整结果回执。守卫拒绝或修正的请求同样记录；回执构造失败时不发布本批次的变量或记录。
6. 将条目写入末楼当前 swipe，发布执行结果并安排保存，再发出通知。通知失败只加入回执的 `warnings`，不改变执行状态。

整个过程同步。返回值是结果对象本身，可直接使用，也可 `await`。

归属是调用时的末楼。流式生成时宿主在处理第一个 token 前已建好回复楼层（1.18 `script.js:3574`、`3802`），生成中调用落在该回复上。ST 原生工具在只有工具调用、没有文字时会先删除空占位回复（`script.js:5354-5355`），此时末楼是用户消息。

### 4.3 文本接口 `applyText(text, { floor, silent })`

1. 解析文本为请求和规则，计算块指纹。
2. 输入块指纹序列与目标楼当前 swipe 的某次文本调用相同，或与完整正文记录的块序列相同时，返回 `skipped`。多次 continue 形成的正文条目按顺序合并比较，不把某一片段误当完整正文。文本接口保留按内容防重；需要有意重复执行相同请求时使用 `apply()`。
3. 作为 `call` 条目（`source: "text"`）追加到目标楼。末楼走临时存储执行与统一发布；历史楼层追加后重建，并返回该条目在重建中的执行结果。
4. 文本来源请求可产生受管根、声明规则。内部执行服务同步完成提交并产生 `{ atoms, errors, skipped }`；公开 `LWB_StateV2.applyText` 保留旧接口的 Promise 返回类型，支持 `await` 与 `.then()`，不把提交延后。`silent` 控制是否发出通知。

### 4.4 重建 `rebuild()`

目标是当前末楼。

1. 计算各楼记录的前缀摘要，计算新的受管根集合。
2. 确定本次要保留的候选楼层（不超过末楼的最高两个）；选择摘要相符的最新检查点作为起点。如果缺少较早的候选检查点，起点须在它之前，才能在重放中补建。没有可用起点则从空状态开始。
3. 保留已有且有效的候选检查点。
4. 在内存临时存储中逐楼按条目重放：变量以解析后的对象保存，执行器通过存取接口读写，不逐条序列化。经过要保留的候选楼层时，复制当时的变量与规则生成检查点。
5. 发布：新受管根写入重放结果；此前受管、现在不再受管的根删除；规则表中这些根下的规则替换为重放结果；其他变量和规则不动。写入检查点（最多两份）。
6. 安排保存。

完整输入、请求记录、临时变量与检查点都在发布前准备好。无论实时追加还是重建，准备失败都不发布半份修改。到达检查点候选楼层时，由请求重放生成缓存，不直接复制混入原生写入的当前变量。

重放时，每条 JSON 来源请求按它之前的记录判定根是否受管，与实时调用在同一位置看到的范围一致；之后的记录不影响它。重放到某楼的结果因此只取决于该楼及之前的记录，检查点可按前缀摘要缓存。发布时只采用整段记录派生的受管根范围；失败时还原运行期守卫表并报告。

### 4.5 可替换的本楼提交 `beginTurn()`

`beginTurn` 的外部流程见 README。领域所有者是变量模块；预设只负责请求组装与触发，核心层不识别任何预设模式。

本接口的唯一持久事实是在目标 swipe 的调用条目上标记 `scope: "turn"`。每个 swipe 最多一个这样的条目；普通调用、正文、初始化不使用该标记。撤销时保留原位置的空条目，随后 `commit` 替换同一位置，保持与同楼其他调用的先后关系。空条目必须持久化，否则刷新后无法知道重写应放回哪个位置。删除该 swipe/楼层时随既有记录一起删除，不新增表、快照或迁移分支。

请求句柄、目标身份及基线签名仅存于内存。真实撤销和替换都复用已有重建器；提交先在内存重建，全部操作通过后才发布。无本楼条目时不重建、不回滚。运行期检查保护异步结果不落到已变化的聊天、正文、swipe 或变量上。

### 4.6 提示词中的只读宏

宏的格式选择和参数示例统一见 README 的“先让 AI 看到当前变量”与“在工具参数里读取变量”。`var-commands.js` 负责读取与格式化，`varevent-editor.js` 在宿主提示词组装事件中应用替换。

`CHAT_COMPLETION_PROMPT_READY` 的文本 `content`、多模态文本段、`mes`，以及 `GENERATE_AFTER_COMBINE_PROMPTS` 的 `prompt`，共用同一替换入口。`dryRun` 也展开只读变量宏，读取当时的真实变量；它不负责回滚，重写适配器应先完成 `beginTurn`，再组装提示词。

`dryRun` 不处理 `<varevent>` 事件块，不入队、不执行脚本、不因这次读取保存元数据。正式生成仍按原流程收集事件并在回合结束后执行。不能把整个提示词处理器在 `dryRun` 时提前退出，也不能为了展开宏而放开事件副作用。

### 4.7 保存与通知

- 保存：运行期 1 秒防抖，调用 `getContext().saveChat()`，一次保存同时写入消息 `extra` 与聊天元数据。生成中也照常安排；宿主保存会等待进行中的保存结束后再执行（1.18 `script.js:9352-9379`，1.14 `8731-8757`）。
- 宿主保存在内部捕获并记录错误，调用方无法得知落盘结果。因此 API 结果不含保存状态。
- 通知：沿用 `xiaobaix:variables:stateAtomsGenerated`，携带执行器的内部事件数据，与 JSON 返回回执深隔离。JSON 调用的通知异常放入 `warnings`，已完成操作保留；文本接口保持原有字符串错误列表。

## 5. 旧数据转换

对象：正式线上已有的 `stateLogV2` v1（逐楼请求记录）及其 v1 首楼初始化检查点。样本包括 [v1 请求](<../tests/fixtures/state2-wal-v1.json>)、[成功初始化旧存档](<../tests/fixtures/state2-wal-v1-init-complete.jsonl>)和[只有规则的旧存档](<../tests/fixtures/state2-wal-v1-init-rules-only.jsonl>)。

时机：打开聊天时，检测到 `stateLogV2` 即转换。写入入口先构造未发布的转换视图，用它识别已执行正文与 continue 新增块；只校验真正的新输入，校验通过后才发布转换。换到无记录 swipe 时，正文输入也在发布转换前完成校验。

规则：

1. 对日志中每个楼层 `F`：
   - `F` 超出当前消息数：丢弃。这些条目在旧版恢复中从不参与。
   - 该楼当前 swipe 已有记录：跳过。
   - 否则写入一条正文条目：`rules`、`ops` 原样搬入；`blocks` 由旧 `signature` 得出。旧签名是各状态块原文拼接，对签名串重新查找状态块即得各块原文，再计算指纹。
2. 旧 `ops` 没有来源标注，按文本来源处理。旧 `roots` 为数组时保留其接管事实，包括明确的空数组；只有旧记录缺失有效 `roots` 时，才按正式版原有规则从请求和规则声明补出。所有原始请求均保留，不因旧请求失败而裁掉。
3. 首楼的旧日志项和当前记录都不存在时，可读取正式版 v1 检查点的第 0 楼初始基线。旧版处理无状态块的开场白会删除该楼日志，但留下此前初始化的检查点：
   - 仅规则表中有明确声明的根构成恢复范围；不从后续请求追溯接管其他根，不复制快照中的无关原生变量，也不使用当前变量值补初值。
   - 将该范围中实际存在的旧值转换为整体 `set`，随后恢复原规则表，保存为首楼的普通文本调用条目。先值后规则，避免拿后来的约束重新拒绝或截断已承认的历史值。只有规则而没有值时只恢复规则，不补造数据。
   - 已有首楼日志（包括明确的空 `roots`）或当前记录时，不用检查点覆盖。未知检查点版本不解释；受支持候选的格式损坏则转换失败。旧快照没有前缀摘要，不声称通过当前摘要验证；转换后按当前记录生成摘要。
4. 删除 `stateLogV2`、`LWB_STATE_APPLIED_KEY` 和旧检查点。不重放，不改变当前变量值。旧检查点只在上述转换入口读取，不参与日常恢复。
5. 所有条目先在内存中构造完毕再统一写入，然后安排保存。构造过程出错则不写任何内容，保留旧数据，本聊天的变量 2.0 写入返回 `legacy_conversion_failed`。
6. 转换可重复执行：保存前页面关闭，下次打开会对同样的旧数据得出同样结果。

转换后的效果：

- 旧版 `applyText()` 写入的记录与正文记录共用楼层，转换为该楼的正文条目，与旧版行为一致。
- 非当前 swipe 没有旧记录，切换到它时按 2.3 由正文解析。
- 第一次重建没有可用检查点，从第 0 楼重放一次，之后按 4.4 补建。

退出条件：确认正式线不再有 v1 存档时，删除转换模块。

## 8. 验收

| 契约 | 验证 |
| --- | --- |
| 请求而非结果 | 数组每楼追加一项，记录体积随楼层线性增长；检查点至多两份 |
| 输入校验 | 跨 realm 对象与同 realm 对象结果相同；不合法整批不执行 |
| 同步 | `apply()` 返回后立即读到新值；相同调用两次各执行一次 |
| B 语义 | 改普通文字不变；删光状态块不变；修改、删一块、continue 追加按 2.2；坏输入保留原状态 |
| 顺序 | 生成中调用、正文、生成后调用、多次 continue，重建结果与实时结果一致 |
| swipe | 新 swipe 不继承旧记录；切回旧 swipe 恢复，正文已删状态块也能恢复 |
| 删除与检查点 | 删除中间楼层、移动消息、删除越过两份检查点；有检查点与无检查点重建结果相同；重建后检查点补齐 |
| 旧数据 | 用 v1 fixture：转换后当前值不变，重建结果与旧版恢复一致；转换失败不破坏旧数据；重复打开不重复转换 |
| 受管范围 | JSON 不能操作未受管根；删除初始化楼后，不再受管的根被清除，独立变量不动 |
| 宿主 | 1.14 与 1.18 实际构建包，单聊与群聊：调用、编辑、换 swipe、删除、重开 |
| 性能 | 3000 楼的小状态、长数组、千键对象：有检查点重建与从零重建耗时 |
