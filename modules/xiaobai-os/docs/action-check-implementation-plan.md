# Dice 行动检定：施工与验收方案

日期：2026-09-14。状态：行动检定 G1–G5 已实现并注册到 Dice APP，详见 [完整施工验收](./action-check-g2-g5-verification.md)。使用自管全局显示正则，完整开标签出现后才隐藏；半截标签不列为门槛。随机遭遇仍是后续批次。

## 1. 本次交付边界

本方案只落实 [Dice 总设计](./dice-app-target-design.md) 中的行动检定，随机遭遇另写施工方案。最终仍是一个 Dice APP，不因分批施工拆成两个 APP。

目标闭环：主 RP 模型在关键行动处输出检定请求 → 本地 D20 → 保存确认 → 结果进入主 API 续写 → 卡片和后续叙事留在原 AI 候选回复。

以总设计中的“无属性 D20、按聊天保存开关、默认关闭”为已批准的施工基线。没有状态栏读取、D100 空分支、独立 Agent API、原生 tool calling 分支或酒馆自动续写协调器。

第一批只创建行动检定实际使用的数据和开关；不创建随机遭遇字段、空 provider、灰色按钮或未使用的公共骰子引擎。后续随机遭遇接入后再补齐总设计的双开关页面。测试线未上线格式直接保持当前干净形态；若中途真实发布，再按实际发布格式决定升级边界。

## 2. 证据账本：哪些已经知道

既有实验见 [同楼续写验证报告](./roll-native-continuation-verification.md)。以下证据不能相互替代：

| 事实 | 证据 | 对施工的约束 |
| --- | --- | --- |
| JSON → 本地结果 → 原生 continue 可留在同一楼 | 隔离宿主的流式／非流式、连续两次检定实测 | 可以沿此路线施工，但不是完整 OS 验收 |
| 探针不是正式协议 | `output/playwright/roll-native-gate/probe.js:34` 使用 `ActionCheck` 和数值 `dc`，固定骰点 7；`:69` 附近使用 D0 结果注入 | 正式专属标签、五档难度、真实 D20、D1 投影都要重新验收 |
| 完成事件早于宿主彻底释放 | 宿主 `public/script.js:3696`、`:3749`、`:5381` | 事件回调不能被当作最终保存屏障 |
| 流式显示直接进入消息格式化 | 宿主 `public/script.js:3656`；报告中的分块泄漏实验 | 只在最终消息处删 JSON 不合格 |
| 普通 `saveChat` 可能吞错误 | 宿主 `public/script.js:9354` | 不用其 Promise resolve 作为落盘证明 |
| OS 已有带确认结果的聊天保存 | `host/sillytavern-chat-save.ts:20`、`:52`，已被 metadata 和 Messages 使用 | 复用公共保存入口；成功不重复整聊读回，未知结果再核实 |
| 新 swipe 可能继承未知 extra 字段 | 宿主 `public/script.js:10061`；已有修正后实测 | 清除新候选的 Dice 工作字段，同时保留旧候选记录 |
| 群聊在一个 wrapper 内连续生成多个成员 | 宿主 `public/scripts/group-chats.js:1049` | 等整个 wrapper 结束可能已换了最后一楼，不能照搬单聊等待逻辑 |
| `MainGenerationRuntime` 只提供忙闲状态 | `host/main-generation-runtime.ts:21`、`:51` | 它不是“生成和保存全部完成”的 Promise，也不代替候选身份核对 |

文中 `host/`、`apps/` 等短路径相对 `modules/xiaobai-os/`；`public/` 指当前 SillyTavern 根目录下的宿主文件，均只读核对。

## 3. 先过宿主门槛，再铺生产功能

G0 是可运行的小范围接入验证，不是先造一个完整原型 APP。沿用仓库忽略目录下的隔离测试环境，使用本地模拟供应商，不读取真实用户聊天和密钥，不请求付费模型、不修改宿主源码。

2026-09-14 实施结果见 [G0 宿主接入记录](./action-check-g0-verification.md)：converter 方案已放弃；采用用户已批准的自管全局正则。用户明确只需在完整开标签出现后隐藏，移除此前人为增加的首字符零闪现要求。公共保存及双成员群聊成功路径证据继续有效；正式生产闭环仍须逐项实现与验收。

### G0-A：生产显示接法

输入正式 `<xb_action_check>` 标签形状，逐字符拆分开标签、JSON 和闭标签，并保留正常正文作为对照。完整开标签之前按普通文本显示；之后过滤专用标签及其 JSON。验收观察浏览器实际显示和解析原文，不只断言最后一次 DOM。

必须同时证明：

1. 完整开标签出现后，协议及 JSON 不再进入显示；允许此前半截标签短暂显示，不吞掉普通 `<`。
2. 原始模型输出完整留给解析器，正常正文、用户消息、代码示例和其他插件 UI 不被错误删除。
3. 显示挂钩可注册、注销，重启／重载后恢复；宿主重建 Markdown converter 后仍有效。
4. 仅维护固定 ID 的一条全局显示规则，明确随酒馆设置保存；不写角色／预设、不修改其他规则。常规检查不写设置。
5. 开启宿主标签转义、自动 Markdown 修正、流式淡入以及用户显示正则时，保持上述契约；不偷偷关闭这些用户设置。

采用用户已批准的原生全局正则入口。当前 converter 扩展缺少消息来源且重建后丢失，已由实验否定；不再保留为生产备选。

规则 ID 为 `xiaobai-os-dice-action-check-display`，名称为“小白 OS · 行动检定显示（自动管理）”，仅 AI、仅显示；不负责解析执行、投骰、保存或请求模型。原始正文不变；不再匹配开标签的部分前缀。

维护发生在启用及每次真实主生成前：只检查内存列表，自有规则缺失／禁用／损坏时补齐并保存；正常检查不发设置请求，不刷新整个聊天或正则 UI。功能关闭后不自动补回；已有显示规则保留以隐藏历史残留协议。全局规则不等于给所有聊天开启检定，执行仍由当前聊天开关限定。

它是 Dice 所有的持久配置，不是临时态：宿主没有独立的运行期规则槽，规则须经原生设置入口参与重建与重载。设置保存失败时应如实提示，不把内存存在说成已持久化；不得开启用户禁用的整个正则扩展。显式卸载清理只删除本 ID；直接删除插件后无法运行清理，需说明在酒馆全局正则中手动删除该名称。所选聊天的数据清理不移除其他聊天仍可能需要的全局显示规则。

用户已明确接受完整开标签出现后再隐藏，`<`／`<xb_` 等不完整前缀不处理；这不是剩余阻塞。标签继续使用 `<xb_action_check>`，与 `<tool_call>` 一样是文本 JSON 的包装，不是供应商原生工具调用；不同时支持两套标签。

通过原生 UI 在流式途中删除规则，酒馆会重载聊天；实测未完成 AI 回复消失，流式处理器报错。下一次检查可以恢复规则，不能恢复已经被宿主重载打断的生成。使用说明须提醒生成期间不要编辑／删除显示规则；不为此替换宿主删除流程或每 token 检查。

显示边界已经确认，按此继续施工；不再为半截标签、普通 `<` 或在途手动删除另造协调机制。

### G0-B：稳定完成与保存确认

在真实流式和非流式完成路径中，依次证明：宿主收尾释放 → Dice 安装消息候选 → 公共保存返回明确确认 → 同一候选可以续写。

验证正常确认、宿主仍在保存、保存 HTTP 错误、写入成功但响应丢失，以及确认返回前切聊。`saveSillyTavernChat` 已有确认／未确认分类，G0 不再写另一个上传器、全局 fetch 拦截器或永久写队列。

消息事件的同步回调只捕获完成候选和安排后续处理，必须及时返回。酒馆会 `await MESSAGE_RECEIVED`，不能在这个回调里等待 Generate 完成或调用并等待下一次 Generate，否则双方可能互等。依据：`public/script.js:3740`、`:3750`。

普通单聊的推进条件至少包含宿主生成标记释放、流式处理器释放、宿主保存不忙，以及原聊天／原消息／原候选仍匹配。等待有可取消的截止时间；超时只留下明确错误，不自动掷骰或无限轮询。

### G0-C：群聊同楼归属

至少使用两个连续发言的群成员复现：第一位提出检定、第二位即将接话。必须证明检定结果仍由第一位在原楼续写，且不会覆盖第二位、让成员重复响应或把 wrapper 忙状态当成空闲。

宿主 `force_chid` 能选择成员，但不等于能选择任意历史楼层；`continue` 仍依赖当前消息和群聊执行状态，见 `public/scripts/group-chats.js:1006`、`:1014`、`:1052`。不能把“强制同一角色”误当作“续写同一楼”已经解决。

单聊可以作为开发的第一个纵向切片，不代表自动缩减发布范围。若多成员群聊需要修改宿主或新增较大的轮转协调机制，先汇报证据和影响，由用户决定支持范围；不在此方案里暗中加入一套群聊调度器，也不静默跳过群聊验收。

G0 退出条件：三项均有真实宿主证据，或用户明确确认了经过收窄的支持范围。未满足时不注册可被用户启用的半成品 APP。

## 4. G1：固定请求、规则与记录契约

### 4.1 请求

运输格式只有一种：AI 正文末尾独占的 `<xb_action_check>` 块，内部是一个 JSON 对象。前面是可见行动尝试，闭标签后只允许空白；不采用原生函数工具，也不设置会把整条回复限制为 JSON 的供应商 `jsonSchema`。

| 字段 | 类型与边界 | 含义 |
| --- | --- | --- |
| `action` | 必填非空字符串，最多 240 个 UTF-16 码元 | 本次尝试 |
| `stat` | 必填非空字符串，最多 120 个 UTF-16 码元 | 检定项目名称，不代表已有属性数值 |
| `difficulty` | 必填，五档枚举 | easy／ordinary／hard／very_hard／nearly_impossible |
| `character` | 可选非空字符串，最多 120 个 UTF-16 码元 | 行动者显示名称 |
| `stakes` | 可选非空字符串，最多 240 个 UTF-16 码元 | 成败影响 |

长度沿用旧执行入口的上限，依据 `modules/tavern/shared/action-checks.ts:315`。新协议在解析入口明确 trim 首尾空白，超长、空必填、可选字段为 null／空白、未知字段和错误类型直接拒绝，不沿用旧版截断、任意值转字符串或数值难度兜底。

同一返回只能有一个执行块；代码围栏、行内代码、引用中的标签不是调用。解析返回三类可观察结果：没有请求、合法请求及其正文边界、存在自有协议但结构无效。JSON 字符串里的相似文字属于数据，不可被简单正则误切成第二次调用。

正式解析器的输入必须是当前生成新增的正文区域。历史文本、推理区、用户消息以及重新渲染的内容不进入执行入口。合法的结构不证明模型此前的叙事没有暗示成败；这属于提示词及真实模型质量验收。

### 4.2 规则

难度范围沿用总设计：easy 2–5／ordinary 6–10／hard 11–15／very_hard 16–20／nearly_impossible 21。程序在所选档位内等概率抽取整数 DC，再独立投 D20；1 大失败、20 大成功，其他点数以 `roll >= DC` 判定。默认本地随机源为 `Math.random()`；具体 DC 和骰点一起保存，重试及重载不重抽，既有记录不重算。测试注入确定随机序列，覆盖区间边界与 DC／骰点独立性，不以统计抽样证明规则。

只在请求合法、目标有效、当前候选已执行次数少于 8 且宿主允许进入保存阶段时调用随机源一次。第八次结果仍允许收尾续写；此后拒绝新的检定，不因重新加载、重试或用户点击继续而重置计数。

### 4.3 持久化形状

行动检定这一切片的 `dice` 分区为当前版本标识与 `actionChecksEnabled`，默认 false。字段及版本由 Dice 自有 parser 负责；没有随机遭遇占位字段。

AI 消息的 `extra.xiaobaiOsDice` 保存当前版本与有序 `checks`。每条记录包含：

| 内容 | 用途与保存理由 |
| --- | --- |
| 本地生成的记录 ID | 确认读回、定位卡片、识别同一已执行事实；不由模型提供 |
| 已解析请求 | 重载后仍能解释这一次骰点针对什么 |
| 实际 roll、当时 DC、outcome | 历史检定事实，不能因为下一版规则变化重算成不同结果 |
| 正文 offset 与 prefixDigest | 仅核验原尝试是否仍可沿用骰点自动续写，不参与卡片定位 |

正文将已执行的协议块原位替换为 `[dice:记录ID]`，块前、块后的原文及空白不作清理。这个标记是卡片位置的唯一事实来源，随消息及活动 swipe 一起保存；不保存卡片 HTML。offset 是原请求块起点，prefixDigest 校验此前原文；续写资格同时要求该位置仍有对应标记，检查不参与显示定位。

使用仓库已有 `js-sha256`，不新增依赖或要求浏览器必须处于支持 `crypto.subtle` 的安全上下文。现有依赖及用法见 `package.json:105`、`domains/messages/receipt.ts:1`。这里的摘要只校验本条记录的正文锚点，不建立全聊剧情哈希或回滚其他 APP 状态。

校验失效不删除历史骰点，取消其自动续写资格；卡片仍只跟随正文标记，不附带“原文已变更／保留历史骰点”文案区。移动标记即可移动卡片，删除标记则不显示，绝不猜位置或置底。测试线无标记的旧检定不自动补写；记录保留，但没有定位回退分支。

不保存时间戳、完整 Prompt、卡片 HTML、D100 空字段、第二份候选索引或持久化 pending 状态。当前消息 extra 与活动 swipe extra 按宿主要求同步，唯一更新入口在消息记录适配器中。

G1 退出条件：请求与记录当前格式冻结，合法／非法输入、临界规则、八次上限和锚点编辑行为的公开输入输出测试通过。模型示例只有经过同一解析器执行后才可进入正式提示词。

## 5. G2：消息读写与恢复

### 5.1 目标捕获和写入

运行内目标包含聊天 binding、当前 chat 数组引用、消息对象、活动 swipe、当前生成身份和预期正文。每次异步边界后重新核对，不能仅凭消息数组下标或角色名字判断还是原目标。

保存候选一次性包含：清理协议后的正文、追加的检定记录、活动 swipe 正文和 extra。保留其他扩展字段、宿主统计／推理／附件字段和所有非活动候选；不替换整份 extra 为 Dice 对象。

调用现有 `saveSillyTavernChat(guard, signal)`。guard 在真正派发前确认聊天／候选／正文及取消条件；保存已派发后不因关窗或切聊中断 HTTP，再收到成功也不能推进已失效聊天的续写。公共适配器的 confirmed 只证明该次写入获得确认，不证明返回时当前聊天仍然相同。

公共保存器不代替宿主生成完成屏障。它与本体保存并非服务端 CAS；G0 必须证明 Dice 在本体收尾后写入，并继续遵守单页面、非多端同时编辑的现行边界。

### 5.2 结果分类与用户恢复

| 状态 | 下一步 | 禁止发生 |
| --- | --- | --- |
| 明确 confirmed，目标仍有效 | 展示确认结果，进入待续写 | 无理由再读回整份聊天 |
| 请求未派发或明确 failed | 保留本页同一骰点候选，显示保存失败 | 重新执行随机源 |
| unconfirmed | 按捕获 binding 读回目标消息及候选，核对正文和自有记录 | 在结果未核实前自动重传或续写 |
| 读回与本次结果一致 | 确认为同一次保存 | 再追加一份记录 |
| 读回仍为可核实的旧版本 | 保留未确认状态；仅在用户明确重试且目标未变时重试同一骰点 | 把“暂时没读到”当成绝对未写入 |
| 读回是其他正文／候选，或身份改变 | 停止并提示冲突 | 强制覆盖旧整聊快照、移到新楼续写 |

重试只重用同一份 Dice 业务候选，重新核对宿主当前对象，不把旧的整聊快照覆盖到后来新增的消息上。读回入口属于 Dice 的宿主适配，不从 Messages 的私信协议借壳；可复用现行 HTTP 协议，但不把 Dice 解析塞进公共保存器。

刷新后仅依据已落盘记录恢复卡片。没有确认保存且内存已丢失的骰点不能恢复；不扫描旧协议重新掷骰。存在记录也不自动发请求，只有用户显式“沿用骰点续写”才启动新运行。

### 5.3 swipe、编辑与删除

- 新 swipe 在宿主复制字段后、Dice 消费该候选前清掉继承的 Dice 字段；旧候选的快照不动。具体事件时点必须来自 G0 验证，不能只选一个名称看似合适的事件。
- 切换已有 swipe：恢复其记录与卡片，不投骰、不写文件、不请求模型。
- 再生成新候选：新检定是新事实；不是“重试续写”，不得冒用旧骰点。
- 编辑／删除／新消息使当前目标不再匹配时，取消自动链；保留仍存在候选的已确认事实。
- 分支与导入只接收宿主实际携带的当前格式记录，不补抽、不创建全局结果映射。

G2 退出条件：保存三态、迟到响应、读回、候选同步与清理均通过集成测试；确认后刷新恢复同一骰点，未确认时不会自动调用主 API。

## 6. G3：单条检定链与原生续写

### 6.1 一份运行状态

应用层只拥有一条当前活动链。阶段用单一状态表达，不叠加 `busy`、`scheduled`、`retrying`、`cancelled` 等相互推导的布尔组合：

```text
观察本次主生成
  → 捕获完成候选并返回宿主事件
  → 等宿主收尾、核对目标
  → 解析并生成一次骰点候选
  → 保存确认
  → 新确认骰点播放约 2 秒 D20 揭晓（停止则不续写）
  → 发起原生 continue
  → 观察本次续写（可再次提出检定）

任一步失效 → 结束自动链
保存／网络问题 → 原位置显示可恢复错误，不自动重跑
```

等待和候选只属于本运行；停止后释放监听／定时等待和注入，不为恢复工作队列持久化标志。已确认结果属于消息，不随运行销毁。

### 6.2 接收事件与辨认自己的续写

`MESSAGE_RECEIVED` 只捕获本次完整输出及候选，不在这个宿主等待的回调里执行整个闭环。后续任务必须在宿主收尾后重新检查，而不是认为“安排到下一次定时器”就必然已经空闲。

由本链发起 continue 前，在当前阶段记录这次调用意图和目标；其 `GENERATION_STARTED` 延续当前链。用户新发言、其他新生成、停止或切聊则使旧链失效。不能看到任何 `continue` 就认作自己的请求，也不能每次收到 `GENERATION_STARTED` 都把自己的下一步取消。

dry-run 不更改真实运行身份；quiet、impersonate 和私人信息等非主生成不进入执行链。不能因为公共忙闲状态被后台计算更新，就判定真实生成已经结束。非流式 `appendFinal` 和流式 `continue` 都作为可能的完成类型，但仍需核对本次调用与目标。

### 6.3 Prompt 投影和请求检查

三个投影各自只有一个所有者：

- 请求契约：来自正式 schema 的字段含义、专属标签、输出结束边界，不向供应商注册 native tools。
- 检定领域说明：什么时候有必要掷骰、首版没有属性加成、获得结果后接着写；不覆盖角色身份和现有预设。
- 已执行结果数据：当前候选按顺序的实际请求、roll、DC、outcome；结果数据不外露记录 ID、锚点摘要、存储版本或队列状态。正文位置标记随原文与宿主续写前缀保留；发送边界由 Dice 的 `host/request-filter.ts` 在 `GENERATE_AFTER_DATA` 去掉请求上下文（`prompt` 文本/消息文本块、NovelAI `input`、CFG `negative_prompt`）中的标记，不改保存正文或结果注入。此事件及所需时序已核对 ST 1.14.0 源码，不新增版本分支。

模型文字默认英文；schema 信息不在领域块重复，收尾规则只放一处。字段上限引用实现常量，示例走解析器测试，不把 Prompt 保存进消息字段。这是提示词技能对本批施工的具体要求。

沿总设计使用自有 SYSTEM／IN_CHAT D1 注入，`scan=false`。组装前从已确认事实构建，本请求组装后清除；取消、出错、切聊、关闭功能时同样清理。清理也要归属到对应请求，不能让交错的 dry-run 清掉真实续写尚未组装的结果，或让后台计算拿走该结果。普通无检定聊天只带启用所需规则，不追加一次 Agent 审查请求。

原生 continue 每次仍经过其他扩展的正常生成拦截器。必须从模拟供应商实际收到的请求验证：结果未遗漏、顺序正确、没有跨候选结果，地图／任务／世界／商店资料仍正常存在。不能用内部 Prompt 字符串“包含结果”代替最终请求证据。

请求 Promise 返回也不能单独证明模型写出了后文；错误、被宿主拒绝、空响应或目标变化都需按可观察消息结果分类。已确认骰点不会因此撤销或重投。

G3 退出条件：普通聊天仍为 1 次主请求；单次检定通常为 2 次、两次检定通常为 3 次，且同一个 AI 候选包含对应叙事。第八次后仍能收尾；第九次请求不执行、不继续自动增加调用。

## 7. G4：卡片、错误与最小 APP

正式显示接入使用 G0 已验证方案，不在此阶段再保留第二条临时正则路径。

卡片升级：新骰点确认保存后才进入临时 `revealing` 阶段，D20 停稳后揭晓结果，再释放原生续写。历史／重载／显式恢复直接显示静态结果，不重播也不重投。卡片视觉与生命周期约束见 [D20 卡片验收](./action-check-card-reveal-verification.md)。

卡片从已确认记录投影到正文中相同 ID 的标记，只替换标记自身。宿主流式淡入会将标记拆成相邻 `text_segment`，只允许跨这些原生相邻片段完成标记替换，不跨代码、图片或其他结构。显示层不调用前缀格式化、不读 DOM 反写正文。字段仍用安全文本节点，不将模型文字作为 HTML 执行。

卡片渲染与恢复按钮的动作分离：聊天重绘、分页加载、切换候选、打开 APP 都不触发投骰或 API。卡片挂载与卸载只替换 Dice 标记。保存回调不重绘消息；显示层发现已确认标记尚未进入宿主 DOM 时，才在该楼层没有编辑器、宿主生成已经结束或当前正在揭晓的条件下调用宿主格式化同步。正文与译文数据不回写。正在编辑的楼层不重绘，并取消自动处理资格。

原生自动翻译可能仍保存着执行前的请求块。仅当正文仍停在已确认检定处、译文也有合法的终结请求块时，显示层临时将其投影为相同标记；不猜历史位置、不修改译文存储。再次原生重绘仍可恢复卡片。

新检定揭晓前只调整聊天容器一次，使卡片进入可见区；位于折叠区域时展开其祖先。随后执行原有 2 秒揭晓，不逐帧强制滚动。历史重绘不滚动、不重播；减少动态效果或后台页面沿用直接显示静态结果的行为。

| 用户所处状态 | 显示和操作 |
| --- | --- |
| 正在生成／等待宿主收尾 | 完整开标签起隐藏协议；此前半截前缀允许短暂显示；不显示尚未确认的成功卡片 |
| 保存失败或结果未知 | 原回复附近说明“骰点尚未确认保存”；提供核实／重试保存，不提供重投 |
| 骰点已确认、续写失败 | 卡片保留，提供“沿用骰点续写” |
| 无效或截断协议 | 就地显示未执行原因；不自动请求模型修复 |
| 用户停止 | 不擅自恢复；已确认卡片仍在，显式继续时再验证目标 |
| 原文编辑使校验失效 | 卡片只跟随标记，不加历史提示区、不自动续写；无标记则无卡片 |
| 八次上限已用完 | 保留已有结果，说明没有执行新的检定 |

自动链只在 OS 和行动检定开关均开启时运行。APP 页面只交付行动检定开关、简短介绍和“请关闭酒馆自动续写”的说明；明确 D20 与续写费用，不先摆随机遭遇占位。

开关由 sidecar 确认后生效；默认读取不建文件。关闭 APP／OS 窗口只退出前台页面，不停止聊天后台链；关闭功能或 OS 总开关会取消自动处理资格，保留已确认历史。停用整个插件后不承诺仍能显示自绘卡片。

按前端设计技能检查 320／390px 与桌面、深浅主题、长行动文字、字号放大、焦点、可访问名称、重复重绘和宿主消息编辑状态。测试全绿不能替代查看正式组件的实际画面。

### 数据清理

停用和清理是不同动作。显式清理所选聊天时，先关闭并确认偏好，再移除消息及全部候选的 Dice 字段和 `[dice:记录ID]` 标记并确认保存，最后清分区；保留标记之外的叙事正文、其他 extra 和其他 APP 数据。未确认清理不继续假报成功，重复操作保持幂等。

`AppDataCleanupContext` 只有分区删除能力，Dice 自带消息清理适配；不能只删分区就交付卸载路径。清理通过后注销所有监听、提示词、显示挂钩和恢复按钮，再删除目录及注册。批量清理范围须明确，不自动改写用户全部聊天。
