# 普通小白 OS 信息 APP：终态设计

## 1. 文档性质

本文只固化信息 APP 已确定的产品心智、领域边界和宿主协作方式，避免后续讨论遗失或被小白酒馆既有实现带偏。本文不是施工方案，不提供阶段拆分，也不表示当前已经可以直接开工。

运行实现已接入普通 OS。具体接口、预算、媒体输入边界与验收证据见 [信息 APP 施工方案](./information-app-implementation-plan.md)；本文仍是产品语义的事实来源。

2026-09-05 已确认联系人主线、跨联系人单楼层、编辑删除、媒体范围、必须回应、请求生命周期和原生回合语义，见第 14 节。施工方案据此展开，不再把这些问题重复交给主人选择。

施工前仍须基于本文补齐接口级数据模型、宿主消息写入适配、Prompt 正文、UI 交互稿和最低风险测试清单。协议、预算和接口字段由实现者查证并给出方案；只有实质改变已确认产品行为时才需重新确认。

## 2. 产品定位

信息 APP 是普通小白 OS 中的私人通讯应用。用户在 APP 内选择联系人并连续交流；这些通讯既是 OS 内的长期记录，也是普通聊天剧情中真实发生过的内容，因此需要在正确时间点留下可被 SillyTavern、Story Summary 和后续剧情读取的楼层证据。

它与小白酒馆 Phone OS 的信息 APP 只允许具有相似的用户感知，不共享 Tavern Session、通讯表、manager run、Prompt 组装、DB 或运行时代码。`modules/tavern/**`不进入普通 OS 依赖图。

可以参考小白酒馆已经走通的联系人、会话和失败恢复体验，但明确不继承以下行为：

1. 不采用隐藏式 D1/extension prompt 把通讯偷偷塞给主剧情；通讯必须在发生时写入普通聊天的真实楼层。
2. 不采用固定“文字、图片、语音”三段齐发或固定顺序的机械回复。模型只发送当前人物在此刻自然会发送的消息。
3. 不采用 `silent/unavailable` 加空消息数组的成功分支。每次成功生成都必须有可见回应；“已读不回”也可作为本轮可见内容表达，不建立独立静默状态机。

本次建设也服务于将来拆分、下线小白板的方向。先查清并承接相关用户需求，不把小白板整体搬入 Messages，也不在本次设计确认中删除旧功能或迁移旧数据。

## 3. 终态位置与所有权

本文把领域名称固定为 `messages`，桌面显示名为「信息」：

```text
modules/xiaobai-os/
├─ domains/messages/                 通讯领域、当前持久格式和不变量
└─ apps/messages/
   ├─ module.ts                      APP 与分区注册
   ├─ application/                   联系人、会话、发送与投影用例
   ├─ host/                          Agent、上下文、聊天楼层适配
   ├─ prompt/                        Prompt 结构与回复 compiler
   └─ ui/                            联系人、线程、消息和失败恢复
```

信息 APP 自有：

- 联系人与线程；
- 用户发出的私人消息和角色回复；
- 消息类型与顺序；
- 通讯 Agent Prompt 和输出 compiler；
- 私人信息楼层的投影规则；
- APP Controller、UI 和本 APP 的错误状态。

信息 APP 不拥有：

- Agent 配置和供应商适配；
- persona、角色卡、世界书或 Story Summary 数据；
- SillyTavern 主聊天存储；
- 图片生成、语音播放等共享媒体实现；
- OS Shell、Kernel 或其他 APP 的生命周期。

这些能力只能通过窄 Host/Capability 接口消费。Kernel 不增加联系人、消息类型或私人信息楼层分支。

## 4. 唯一事实来源与状态分类

| 内容 | 所有者与唯一事实来源 | 生命周期 |
| --- | --- | --- |
| 联系人、线程、完整通讯消息 | `messages` sidecar 分区 | 随当前聊天世界线长期保存 |
| 私人信息剧情楼层 | SillyTavern 当前聊天 | 随聊天、分支、删除和导出存在 |
| 楼层与通讯片段的关联 | 楼层 `extra` 中的信息 APP 标记 | 随该楼层存在 |
| persona、角色卡、激活世界书 | SillyTavern 宿主 | 每次请求重新捕获只读快照 |
| 剧情总结、人物弧光 | Story Summary 公开窄接口 | 每次请求按当前边界读取只读投影 |
| Agent 配置 | `agent-core`共享配置 | 用户级长期保存 |
| 生成请求、AbortController、流式文本、typing | 当前 Host 运行 | 不持久化 |
| 尚未确认发送的原始输入、消息 ID、失败状态 | 当前聊天的 Messages Host 运行 | 重进 APP 可恢复；确认入库、明确删除、切聊或停止模块时释放，不承诺浏览器重启恢复 |
| 页面路由、滚动位置、分联系人输入草稿 | 当前 APP 运行 | 返回列表、切联系人保留草稿；退出 APP 后不承诺恢复，不持久化 |

sidecar 分区是 APP 内通讯历史的事实来源；SillyTavern 楼层是这段通讯在主剧情时间线中的事实投影。不能反过来每次解析渲染后的楼层重建 APP 数据，也不能把 persona、世界书正文或人物弧光复制进 `messages` 分区。

## 5. 单楼层通讯投影

### 5.1 一个连续通讯时点只占一个楼层

一次连续的私人通讯过程只创建一个具有下列语义的 Assistant 楼层：

```text
/sendas name="私人信息" compact=false <私人信息>…</私人信息>
```

这里的 `/sendas`描述的是宿主可观察行为。实现可以调用等价的 SillyTavern 消息 API，但不能通过拼接并执行不受控命令文本来逃避结构化校验。

APP 内连续发生的 20 条、50 条甚至更多消息，都追加到该楼层同一个 `<私人信息>...</私人信息>` 容器中。它们在信息 APP 内仍是独立消息，在普通聊天中却只占一个 Assistant role，绝不能每条内部消息插入一个新楼层。

`compact=true`明确不用：它只改变单个楼层的紧凑样式，不会把多条 `/sendas`合并为一个楼层，也会让产品语义依赖 SillyTavern 的小系统消息外观。

### 5.2 连续时点与封存

“一个楼层”不是指整个聊天永久共用一个楼层，而是指同一个连续通讯时点共用一个楼层：

- 当前私人信息投影仍位于聊天尾部，且中间没有新的普通 User/Assistant 剧情楼层时，后续通讯继续更新该楼层；
- 一旦普通剧情继续并在其后形成新楼层，旧私人信息楼层立即成为封存证据；
- 之后再次打开信息 APP 发生通讯时，在新的当前时点创建另一私人信息楼层；
- 禁止回写已经被后续剧情越过的旧楼层，否则后来发生的通讯会被伪造为过去已经发生。

同一连续时点的多个联系人共用一个私人信息楼层，按消息实际顺序标明通讯双方。切换联系人、返回桌面和关闭 OS 浮窗不结束该时点；普通剧情继续即封存旧楼层。用户主动编辑或删除投影后的处理见第 5.5 节。关闭 OS 总开关期间，若该楼已被 Story Summary 纳入长期总结，重新启用后也将其封存，新通讯另起楼，不回写已总结的证据。

### 5.3 原文与渲染

楼层保存的是可读、可导出、可被模型理解的语义原文，最外层固定为：

```xml
<私人信息>
  ……通讯记录……
</私人信息>
```

内部每条消息必须保留联系人、方向、消息类型和正文的明确边界，并进行 XML 转义。具体内部标签在施工文档中定稿；不允许只保存渲染 HTML、CSS 类名或不可读 JSON blob。

渲染层对该容器做专属美化：

- 展示为可展开的通讯记录：联系人、消息数、折叠时的末条预览；短记录默认展开，长记录默认折叠；
- 展开后沿用主聊天滚动，不另套固定高度的内部滚动框；
- 按原始先后显示消息气泡，仅为连续的同联系人消息加分组标题，不每条重复通讯双方；
- 桌面与移动端都不能撑爆普通聊天；
- 渲染失败时回退为可读原文，不能让楼层消失；
- 所有文本按不可信内容处理，禁止注入 HTML。

这是对消息楼层的显示增强，不改变送入 Story Summary 和模型的原文。展开状态只在当前 DOM 生命周期内保留，不写存档。

### 5.4 禁止 swipe

私人信息楼层必须在消息数据中设置 SillyTavern 原生契约：

```ts
extra.swipeable = false
```

SillyTavern 的 `isMessageSwipeable()`会直接尊重该字段，因此这是行为层禁止，不是仅用 CSS 隐藏左右按钮。楼层还需要一个由信息 APP 拥有的稳定 `extra` 标记，以便重新渲染、定位当前可更新投影并避免仅靠显示名或 XML 猜测。

该标记是必要的聊天持久字段：所有者是信息 APP；生命周期与楼层一致；删除楼层即删除标记；卸载 APP 时可保留为普通可读消息，不能要求永久兼容运行壳。

### 5.5 编辑、删除与撤回

主聊天投影和 APP 通讯记录分别管理，不做双向同步：

- 用户编辑或删除私人信息楼层，只改变主剧情证据，不回写 sidecar 通讯历史；
- 用户修改过的楼层不被自动覆盖，删除的楼层不被自动补回；后续通讯另起新楼；
- APP 不提供整段聊天回退、已发送消息编辑或已成功角色回复重抽；技术失败可重试。用户上传的图片另提供单条删除，见下；
- 删除联系人时经确认一并清理 APP 内该联系人的线程、消息及相关派生资料，不删除已存在的主聊天楼层；
- 共用楼层中其他联系人的记录不能因删除某个联系人而丢失；本地数据删除不能触发旧楼层重写。

删除剧情投影不等于撤回已经发送的私人消息。自身投影更新与用户主动修改需要由宿主适配正确区分，不能靠静默改正文避开消息生命周期。

用户上传的图片气泡下提供「删除图片消息」，经确认只删除所选图片及其配文，保留已有回复、后续消息和其他联系人。不再把该原图传给信息 Agent；受影响的线程摘要作废，之后从保留的原文重建。主聊天中的记录和酒馆图库原图不删除，因此这不是剧情回滚。删除必须保存确认后才从 UI 消失；失败/未确认沿用「检查保存」。

「重试」仍在联系人聊天页最后一条待回复消息下方，不重复发送输入：更换支持图片的模型后可直接重试；删除本次失败图片后可正常发文字，删除历史图片后可重试最新文字。不把所有 400 错误判定为不支持图片，也不自动删图或组合“回退并重试”。

## 6. Sidecar 领域事实

`messages`分区至少需要表达以下概念，但本文不冻结 TypeScript 字段名：

- 联系人：稳定本地身份、显示名和必要的用户备注；
- 线程：联系人归属、创建顺序和最后活动位置；
- 消息：稳定 ID、线程、发送方、类型、内容、确定顺序和发生时间；
- 连续通讯片段：用于把若干独立 APP 消息投影进同一个私人信息楼层。

以下内容不进入分区：

- 世界书条目 UID 或“联系人必须对应某条世界书”的绑定；
- 角色卡与世界书全文副本；
- Agent 原始响应、思考过程或 Prompt；
- 当前请求 loading/typing；
- SillyTavern DOM、楼层 HTML 或 CSS；
- “以后可能使用”的联系人画像缓存。

墙钟时间只用于 UI 展示，领域顺序必须有稳定的单调序号，不能因设备时钟回拨打乱消息。

### 6.1 联系人入口

已知人物是确定的主入口；人物来自真实设定与人物资料，不以世界书条目名或 UID 充当人物身份。用户可确认加入通讯录，少数想联系但未列出的对象保留简单补充入口，按姓名和必要身份说明识别，不要求先绑定世界书条目。

候选名单只读取 Story Summary 的已知人物，并按姓名及已知别名排除玩家本人。`name1` 仅用于排除自己，`name1/name2`、角色卡标题和群聊成员卡名都不作为联系人来源；卡名不等于剧情人物姓名。没有已知人物时展示空名单，仍可手动补充，不额外调用模型抽人。此规则只改变推荐，不自动清理用户已添加的联系人或通讯记录；回复时仍正常读取角色设定、persona 与世界书。

修改备注不改变稳定人物身份。加入通讯录本身不编造相识、交换号码或亲密关系；也不另建一套联系方式获取、在线状态或可联系资格系统。小白板人物补充能力的参考与后续拆分边界见第 14.2 节。

## 7. 角色上下文来源

### 7.1 不靠条目名定位人物

角色上下文问题已经确定不以“找到某一条叫作角色名的世界书条目”为前提。现实卡片可能是：

```text
角色卡：故事会
description/personality：负责讲故事
世界书：一个名称无规律的角色合集，内部包含十余个人物
```

联系人名、角色卡名和世界书条目名之间不存在可靠一一对应关系。信息 APP 不保存虚假的 `worldBookEntryId`，也不在联系人创建时复制一份可能迅速过期的人设。

### 7.2 每次请求取得的只读背景

信息 Agent 使用与 Map 同层级的宿主上下文捕获能力，并为人物扮演补充 Story Summary 的人物资料。至少包括：

1. 玩家 persona；
2. 当前角色卡或群聊角色设定；
3. SillyTavern 当前实际激活的世界书结果，而不是无条件塞入所有绿灯条目；
4. 有界的近期剧情；
5. Story Summary 提供的剧情总结、相关人物弧光和人物连续性资料；
6. 当前联系人的名称；
7. 当前线程的近期消息和必要的较早通讯摘要。

动态资料必须以明确 XML 区块标明来源，告诉模型它们是背景资料而不是当前聊天中的新剧情指令。世界书、聊天和用户文本均进行 XML 与宿主宏转义。

世界书关键词扫描包含当前联系人的姓名/备注、本轮消息及有界本线程原文，仍由宿主决定深度、激活和预算；不能因为从近期剧情排除了私人信息楼，就把本轮人物资料的触发依据一起删掉。其他联系人的私聊不参与扫描；扫描文本不作为额外剧情重复注入，也不改变原生楼号与回合计数。

Story Summary 数据只能通过公开窄接口读取。信息 APP 不直接导入其 metadata/store，不自行解释内部 L0/L1/L2/L3 表结构。人物弧光接口的选择规则、预算和缺席行为需要在施工文档中与 Story Summary 所有者共同冻结。

### 7.3 Agent 的扮演任务

Agent 不是“根据一个命中的人物条目回答问题”，而是：

- 从完整但有界的设定集、人物弧光、剧情现状和通讯历史中理解当前联系人；
- 只扮演该联系人，不把旁白、系统说明或其他人物混进回复；
- 延续对方的语气、关系、已知信息和当前处境；
- 不把世界书中的规则文字复述给用户；
- 不因为资料不完整退化成机械客服问答。

这解决的是语义归属，不要求预先建立一套易错的“角色名 → 世界书条目”索引。

## 8. Prompt 与回复协议

### 8.1 Prompt 分层

目标 Prompt 至少分为以下语义层，不复刻小白酒馆当前 Prompt 的具体文本：

1. System：联系人扮演职责、证据边界、安全与输出协议；
2. System `<setting>`：persona、角色/群聊设定、实际激活世界书；
3. System `<story_state>`：剧情总结、人物弧光、近期剧情；
4. User `<private_message_thread>`：当前线程历史与可选通讯摘要；
5. User `<incoming_private_message>`：本轮用户刚发出的消息；
6. User：固定执行命令，要求仅返回通讯回复协议。

设定、总结和历史只能帮助扮演，不能被当作用户刚发来的内容。`<incoming_private_message>`是本轮回复的唯一直接触发证据。

### 8.2 自然分条，而非固定三段

模型一次响应可以包含一条或多条独立回复。每个回复块代表信息 APP 中的一条消息气泡，而不是先把一个连续答案机械切成“文字段、图片段、语音段”。

目标行为是：

- 回复条数由当前人物和语境决定，不固定为三条；
- 不要求每轮同时出现文字、图片和语音；
- 不要求固定的类型顺序或平均分布；
- 短回复可以只有一个气泡；连续补充、犹豫或情绪化表达才自然拆成多个气泡；
- 每个回复块必须能独立编译为一条消息，坏块不能污染已合法的兄弟块；
- 没有合法回复时整轮失败，不能把解释文字或思考过程存入线程。

每次成功的生成必须产生至少一个可见回复块。不继承酒馆协议的 `result: silent | unavailable` 空结果；人物拒绝交流或“已读不回”的表达仍是本次回应内容，不新增延迟回信、重试轮询或定时唤醒机制。网络、Provider 和解析失败仍是技术失败，不伪装成角色不想回复。

协议方向沿用四次元壁已经验证的“从模型文本提取明确回复块，再由本地 compiler 处理媒体标记”，但信息 APP 必须保留多个块的边界；不能像四次元壁当前投影那样把多个 `<msg>`简单合并成一段文本。

具体采用多个 `<reply>`、结构化 JSON `replies[]`，还是其他 Provider 兼容格式，由实现者在施工文档中对照共享 Agent 的 JSON 兼容模式、普通文本模式和流式解析能力后确定。只保留一种当前公开协议，不把技术选型再次当作产品问题交给主人；测试公开输入输出，不做 Prompt 全文快照。

### 8.3 媒体

文字、图片和语音本期全部支持，不把媒体延期；它们是消息类型，不是每次响应必填的三个栏位。

角色发来的图片保存可读内容描述，通过共享画图能力生成；角色语音保存原文，通过共享语音能力播放，点击才出声。媒体生成或播放失败保留消息事实、描述/文字和单独重试入口，不重新生成整轮通讯。不持久化播放/排队状态。

用户输入与角色回复分开：点击「＋」直接打开设备选图器，不弹出文字/图片/语音菜单。选图后有缩略图、移除和可选配文，可以只发图片；原图保存并交给支持看图的回复模型，重开还能查看。发送端不提供录音或“文字转语音”入口。参考小白助手现有附件交互与多模态传图，不依赖其会话模块；原图沿用酒馆用户图库，消息只保存本地引用。删除通讯不连带删除其他分支或原生楼层仍可能引用的图库文件，图片清理由用户单独管理。

## 9. 发送、保存与失败顺序

信息 APP 的完整通讯记录在 sidecar，私人信息楼层是派生投影。因此任何实现都必须遵守：先确认领域事实，再发布对应剧情投影；不能先向普通聊天显示成功，sidecar 保存失败后再假装没有发生。

单次发送时序为：

```text
用户点击发送
→ 立即清空本次输入、显示同 ID 的待发送气泡
→ 若附图，先保存原图到酒馆图库
→ messages 分区确认用户消息
→ 捕获有界角色上下文并调用共享 Agent
→ compiler 得到 1..N 条合法角色回复
→ messages 分区确认回复
→ UI 显示正式回复
→ 一次更新/创建私人信息楼层投影并确认回执
```

需要在施工方案中进一步解决 sidecar 与 SillyTavern 聊天不是同一原子存储的问题。最低要求是：

- sidecar 已确认而楼层投影失败时，APP 明确显示“剧情楼层尚未同步”并提供幂等重试；
- 不得重复保存用户消息或重复生成同一批回复；
- 待发送气泡不冒充存档确认；发送失败留在原气泡重试，不退回输入框、不清掉后来写的草稿；尚未保存且无待确认候选的发送可直接删除；
- Agent 失败时保留已经确认的用户消息，在原气泡提供回复重试；已确认输入仍可尝试同步，同步异常不覆盖原回复失败原因；
- 主聊天同步不作为请求回复的前置条件；常态不展示“正在保存消息/正在写入主聊天”，只有异常才提供相应恢复入口；
- 用户消息已确认后，返回桌面、切换 APP 或关闭 OS 浮窗不取消回复；请求属于当前聊天的 APP Host，重新进入可查看结果；
- 切聊、关闭 OS 总开关或当前聊天开始主剧情生成时，停止尚未完成且未进入保存的回复；保留已经确认的消息，之后由用户明确重试并重新捕获当前上下文；
- 已进入 sidecar 保存的结果等待真实确认，不伪报取消或回滚；保存确认后的楼层投影也必须遵守封存、聊天身份和主生成写入边界；
- 切聊后任何迟到回复不得写入新聊天。

这些是施工设计问题，本文不虚构已经存在的跨存储事务。

## 10. Story Summary 与主剧情

### 10.1 不使用 D1 隐藏注入

私人通讯不额外注册 D1 `<private_messages>`之类的主剧情 Prompt。它通过真实的“私人信息”Assistant 楼层进入普通聊天上下文，因此：

- 发生顺序可见；
- 用户能编辑、删除、分支和导出普通聊天；
- 后续主剧情与 Story Summary 读取的是同一份楼层证据；
- 不会同时存在“可见楼层一份、隐藏 prompt 又一份”的重复注入。

### 10.2 L0 已核实的行为

Story Summary 的 L0 增量提取逐个处理非 User 楼层，不要求聊天严格保持一组 `U+A`：

```text
U + A + 私人信息A
```

第一个 A 可以结合紧邻的 U 提取；后一个私人信息 A 在前一楼不是 User 时，会作为独立 Assistant 楼层提取。这种 `U+A+A`结构本身不会漏掉私人信息楼层。

同一尾部私人信息楼层被追加时，必须走 SillyTavern 正式消息编辑/更新生命周期。Story Summary 已有编辑失效路径，会从受影响楼层作废精确依赖旧正文的 L0/L1 派生数据并安排补齐。实现不得直接改 DOM 或静默替换 `chat[].mes`而不派发宿主事件。

L2 不会因普通正文编辑自动回滚，因此必须在生成入口避免提前总结尚在追加的私人信息尾楼。Messages 在后台生命周期注册运行内的“稳定源截止位置”，Story Summary 的自动、手动总结及提交前复核都遵守它；普通剧情在后面形成新楼后，完整通讯才进入下一次总结。该保护依据原生楼层标记，不等待 sidecar 加载；有标记的尾楼保守延后，不新增持久锁或待总结字段。

OS 总开关关闭时注销该边界；若此时尾楼已被总结，重新启用后通过 Story Summary 公开的已总结截止位置识别并封存，不能继续追加。关闭浮窗不停止后台注册，不影响正常连续通讯。这里只修复追加中证据的消费时序，不扩大 Story Summary 的历史编辑回滚契约。

旧投影一旦被后续普通剧情越过便封存，避免不断编辑历史楼层和反复破坏已经形成的时间证据。

### 10.3 与 Map/Tasks 接受轮的关系

私人信息楼层是实际 Assistant 消息。下一条普通 User 消息确认上一轮时，Map/Tasks 的接受轮捕获可以把它作为同一时间段的剧情证据；信息 APP 不另发维护事件，也不直接修改 Map 或 Tasks。

### 10.4 原生回合语义

私人信息楼层沿用 `/sendas` 的原生 Assistant 楼层语义，算一回合。不为了信息 APP 在银行、回合计数或其他消费者中新增“排除私人通讯”规则。

新增一个私人信息楼层计一个 Assistant 楼层；同一楼层追加二十条内部消息仍然只有这一楼，不凭气泡数量制造额外回合。银行、商店等继续消费各自现行的计数或生成生命周期；信息 APP 不手动补扣道具、不伪造主生成事件，也不改写这些领域的现有规则。

## 11. 分支、切聊与多设备

- 创建历史分支时，Messages 在子 sidecar 首次保存前，按子聊天仍保留且正文摘要匹配的私人信息标记裁剪通讯前缀；不能直接继承父线最新完整分区，包括稍后首次打开子线的情况。裁剪规则属于 Messages，Kernel 只提供复制前的窄回调。
- 子线只继承保留消息涉及的联系人，清空无法定位到分支点的可变备注和线程摘要；之后按保留原文正常积累摘要。不带入没有通讯证据的通讯录条目；没有合法私人信息标记时，从空通讯记录开始。父线不受影响，也不从原生楼层复活父线已删除的 APP 数据。
- 继承片段封存，新通讯另起楼；保留原单调序号的高水位，防止与继承楼层标记发生序号复用。普通完整复制/导入不按历史分支裁剪；其他 APP 仍遵守自身原有复制规则，两个 sidecar 后续独立。
- 切聊立即取消旧聊天尚未归属完成的 Agent 请求；迟到结果只能被旧 identity guard 丢弃。
- 使用当前页面已确认的通讯事实，保存依赖明确服务端响应；正常发送不下载/比较整份主聊天，只有未确认投影恢复才核实目标楼。切聊重新加载，不承诺多设备同时编辑。
- 楼层投影关联不能只保存 mesId，因为插入、删除和分支会改变序号；必须结合稳定 APP 标记重新定位并校验聊天身份。
- 打开信息 APP 可以读取本地/sidecar 状态，但不得自动发送消息、测试 API 或生成联系人回复。

## 12. APP 体验与故障隔离

目标界面至少包含联系人列表、线程页、消息气泡、输入区、发送状态和失败重试。视觉沿用当前普通 OS 的系统质感与深浅主题，不复制小白酒馆 Phone OS 组件。

列表顶栏仅保留「信息」与添加入口，下面是搜索和联系人；不添加口号、副标题或联系人数页脚。线程顶栏保留头像、姓名与详情入口，不重复标注「私人对话」，空线程不填寒暄。页面使用清晰白底/中性深色与绿色发送气泡，正文、草稿预览、媒体、错误和恢复操作保持完整。

体验约束：

- APP 打开立即出现壳与本地状态，不能等待 Agent 才显示；
- 正在发送时同一动作不可重复点击；
- 多条模型回复按独立气泡逐条展示，不机械平均间隔；
- 线程很长时由 APP 内虚拟列表/分页处理，不能一次把全部 DOM 塞入页面；
- 普通聊天中的投影仍只有单个限高滚动容器；
- Agent、人物上下文、媒体或楼层投影失败只影响信息 APP，不让其他 APP 或 OS 桌面消失；
- 内部 Provider、Prompt 和存储错误只记日志，UI 使用稳定本地文案。

## 13. 当前明确不做的事

- 不引用 `modules/tavern/**`运行时代码；
- 不把 Tavern Phone DB 或通讯历史迁入普通 OS；
- 不建立 server plugin；
- 不把信息 APP 做成 Map/Tasks 自动维护 participant；
- 不在扩展页增加“信息 APP”勾选项；它和银行、地图一样是 OS 桌面 APP；
- 不为测试线旧实现保留 schema、入口或 Prompt 兼容壳；当前没有普通 OS 信息 APP 历史数据；
- 不把世界书全部条目无界塞进请求，也不以条目名做人物身份事实；
- 不新增角色静默/不可联络状态机、自动追问、定时回信或主动来信；
- 不为了信息楼层新增回合排除规则，也不借本次建设改造酒馆已有的信息 APP；
- 不把小白板旧 UID 绑定、短信回写世界书或世界推演整体引入 Messages；
- 不用 Prompt 全文或单词快照代替行为测试。

## 14. 已确认决定与施工责任

### 14.1 主人已确认的产品决定（2026-09-05）

1. 已知人物主线确定；少数未列出的联系人参考小白板的补充入口。建设方向服务于小白板将来拆分下线，不要求另造复杂的人物发现系统。
2. 同一连续时点跨联系人共用一个私人信息楼层。
3. 主聊天编辑/删除与 APP 历史分开，不双向同步、不自动复活投影；不编辑成功消息、不重抽成功回复。后续确认允许删除用户上传的单条图片消息，不回退其他聊天；删除联系人清理本地通讯，不删主聊天证据。具体边界见 5.5。
4. 文字、图片、语音全部支持，参考小白酒馆实际实现，不固定三段齐发。
5. 每次成功生成必须有可见回应；“已读不回”也用内容表达，不建立空成功或静默状态分支。
6. 离开界面继续已发送请求；切聊、关总开关或开始主剧情生成停止未提交的回复；已确认消息保留，已发出的保存如实落定。
7. `/sendas` 新楼层自然算一回合；同一楼层追加不新增回合，不为信息 APP 创建排除规则。

原则：复杂度用于上下文准确性、消息事实与时间线一致性、保存恢复和错误边界；不用于模拟通讯资格、静默或额外回合制度。

### 14.2 现有实现参考与小白板后续拆分

- `modules/story-outline`：已核对到陌生人提取、普通/重要 NPC 设定生成并写入世界书、联络人添加、短信与摘要。旧联络人入口要求世界书 UID，旧短信还会回写世界书的 `SMS_HISTORY` 区段；新信息 APP 不继承这些前提或存储路径。
- 小白板补充人物、加入联络人、再联系的用户需求列入后续拆分清单；“补一个未列出的联系人”不等于默认自动生成一份完整人物档案。NPC 创作、世界推演等能力的归属和旧数据处置要单独核实，不借通讯建设整包搬迁或直接删除。
- `modules/tavern/.../messages`：参考联系人/会话体验和三种消息的媒体交互；不继承 Tavern DB、人物记忆路径绑定、请求租约、固定条数上限或 `silent/unavailable` 分支。
- `apps/fourth-wall`：参考主剧情与独立会话历史分层、请求取消和媒体编译思路；不继承皮下角色职责、多块合并或把未解析文本作为成功回复的回退。
- `host/prompt-context` 与共享 Agent 是普通 OS 已有能力。现有上下文捕获提供 persona、角色设定、世界书激活结果、近期剧情和 Story Summary 有界事件；人物弧光仍需 Story Summary 自己提供公开窄接口，不误称四次元壁已经提供全部上下文。

本轮只更新设计确认，不删除小白板、不迁移其联系人/世界书/短信，也不修改酒馆信息 APP。

### 14.3 实现者须完成的技术设计

接口级模型、跨存储投影恢复、回复协议、流式显示与确认保存的交接、上下文预算、Story Summary 人物资料接口、长线程摘要的更新与删除、媒体输入与资产生命周期，由实现者基于实际代码完成施工设计。凡新增持久实体，必须说明事实来源、必要性、所有者、失败处理和删除路径；不把这些实现问题重新包装成主人需要选择的问卷。

## 15. 删除路径

删除信息 APP 时：

1. 停止本 APP Agent 请求、媒体和渲染增强，注销稳定总结源截止位置回调；
2. 从 Host/Shell catalog 删除 `messages`注册，并移除生产组合中的 Messages 分支复制回调；
3. 删除 `apps/messages`、`domains/messages`及测试；
4. 通过一次明确数据清理删除 `messages`分区，或按产品选择保留为不可再写的导出数据；
5. 已存在的私人信息楼层保留为普通可读聊天正文，移除专属渲染后仍显示 XML 原文。

不得在 Kernel、Agent Capability 或 Story Summary 中留下识别信息 APP 业务的永久分支。

## 16. 实施边界与后续维护要求

第 14 节产品决定已经确认，[施工方案](./information-app-implementation-plan.md)已回填当前实现、接口和验收证据。后续改动继续遵守下列边界，不能把未验证的外部媒体或实体 WebView 能力当成已经验收：

- 功能所有者：`messages`领域与信息 APP；
- 唯一事实来源：sidecar 完整历史、SillyTavern 时间线投影；
- 临时态与持久态：本文第 4 节；
- 外部依赖：Kernel、Agent、宿主上下文、Story Summary、聊天写入/渲染、共享媒体；
- 注册入口：APP module、分区、Host/Shell catalog；
- 删除路径：本文第 15 节；
- 兼容对象：只有现行 SillyTavern/浏览器/Provider/sidecar 环境，无测试线旧信息数据；
- 最少必要测试：跨联系人单楼层不刷屏、封存/用户修改后不回写、禁止 swipe、原生楼层计数、切聊/主生成拒绝未提交迟到回复、上下文分层、必须回应与可变回复块、媒体失败不损坏消息、Story Summary 正式事件链和跨存储失败恢复。

施工不得再次从“先做一个能聊天的页面，以后再补楼层和上下文”开始；第一版就必须处在本文规定的领域、时间线和故障边界内。
