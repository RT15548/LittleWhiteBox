# 小白 OS Dice：行动检定与随机遭遇设计

日期：2026-09-14。状态：行动检定已完成并注册为 Dice APP，含同楼卡片、保存确认与原生续写，见 [施工验收](./action-check-g2-g5-verification.md)。随机遭遇、状态栏与世界／总结增强尚未施工；本文保留这些后续目标，不代表已经实现。

## 1. 终态与首版范围

Dice 是普通酒馆小白 OS 中的一个独立 APP，先容纳行动检定和随机遭遇。主 RP 模型判断行动是否需要检定，Dice 执行随机规则、保存结果，并把结果交还主剧情；不接管主聊天 API，也不充当另一位剧情生成 Agent。

未来可以在同一 APP 内加入状态栏，让检定读取角色属性；随机遭遇可以读取世界 APP 与剧情总结，获得更丰富的素材。这是功能边界，不是首版要建立的空接口或占位数据。

本文承接 [OS Kernel 终态设计](./os-kernel-target-design.md)。同楼续写的已有证据见 [Roll 原生续写验证](./roll-native-continuation-verification.md)。本文是目标与首版设计，不把隔离探针记为正式功能交付。

行动检定的单独施工批次、宿主门槛与验收清单见 [行动检定施工方案](./action-check-implementation-plan.md)。先实施行动检定时只创建其实际字段和开关，随机遭遇接入后再补齐本文的双功能终态，不提前注册占位能力。

### 1.1 已确认的产品决定

- 两项能力放在同一个 OS APP，不在扩展设置中继续堆独立入口。
- APP 页面只有必要的介绍和两个独立开关；具体玩法在主聊天里发生。
- 行动检定走主 RP 模型的 Tagged JSON、本地掷骰、酒馆原生 `generate('continue')`，后文接在原 AI 楼层。
- 不调用独立 OS Agent API 审查每轮聊天是否需要掷骰。
- 随机遭遇提示是已有用户楼层的附属 UI，不创建额外聊天消息，也不是无归属的楼间节点。
- 使用行动检定时，用户需要关闭酒馆自带的“自动续写”。只说明此限制，不自动修改用户设置，不实现二者的协调器。
- Dice 自动维护一条会随酒馆设置保存的全局仅显示正则；启用及生成前检查，缺失／禁用／损坏才修复。关闭功能后不自动补回，正常检查不保存设置。
- 完整 `<xb_action_check>` 开标签出现后才隐藏协议，半截标签按普通文本显示；不要求从第一个 `<` 开始隐藏。标签名称已获用户接受。
- 状态栏、世界／总结增强属于后续调整，本次先迁移两项现有玩法。

### 1.2 本设计提出的具体选择

以下最初为本稿建议；用户随后批准按行动检定施工方案开工，作为当前施工输入：

- 工作名为 **Dice（骰子）**，APP id 为 `dice`；不扩展命名讨论，也不与“游戏”APP 的大话骰合并。
- 首版使用旧版已有的无属性 D20 规则。OS 当前没有对应状态栏来源，不移植空的 D100 属性分支，不把变量面板假定为角色属性。
- 两个开关默认关闭，按当前聊天分别保存。旧版两个默认值均为开启；这里有意改为用户主动启用，避免更新后自动增加玩法和续写请求。
- 行动检定覆盖普通单聊与群聊；正式实现已独立验证双成员流式／非流式轮转及失败恢复。随机遭遇的群聊行为仍需其自身验收。

本版不做手动掷骰台、骰子商城、事件池编辑器、概率／冷却编辑器、独立历史页、属性编辑器或新的 API 配置页。

## 2. 两项能力的行为

### 2.1 行动检定

主 RP 模型在有不确定性且结果会改变后续剧情的行动处请求检定。模型描述尝试、提供行动与难度，先停在结果揭晓之前；本地程序掷骰并确定结果，模型再根据已经确定的结果续写。

迁移依据：`modules/tavern/shared/action-checks.ts:75` 的检定时机、`:250` 的请求字段和 `:311` 的本地执行路径。

首版规则保留旧版 D20 行为：

| 难度 | 成功目标值 DC |
| --- | --- |
| easy | 5 |
| ordinary | 10 |
| hard | 15 |
| very_hard | 20 |
| nearly_impossible | 21 |

骰面为 1–20；1 为大失败，20 为大成功，其余以 `roll >= DC` 判断。临界规则优先，因此最高难度仍可在掷出 20 时大成功。依据：`modules/tavern/shared/action-checks.ts:58`、`:127`、`:141`。

`stat` 在这一版只是检定项目名称，例如“敏捷”，不代表已经读取或计算了角色敏捷数值。UI 与提示词均不能宣称“已计入角色属性”。未来属性接入时再加入实际存在的 D100 规则和资料投影。

一次模型返回最多请求一次检定；同一个 AI 候选回复可先后检定多次，总上限为 8 次，按该候选已保存的检定次数计算，重载或重试不清零。每次先保存结果再继续；第八次结果仍允许一次收尾续写，但不再接受新检定。若模型继续提出第九次请求，不投骰、不再自动加请求，并给出可见说明。旧版工具循环上限为 8，本设计将其收敛为单候选的已执行次数上限；依据：`modules/tavern/app-src/runtime/run-once.ts:149`。

开关关闭时不请求或执行新检定，已经发生的骰点记录不因此删除。

### 2.2 随机遭遇

沿用旧版的触发机制，而不是新增事件生成系统：

- 对新用户回合，在首次实际主 RP 生成前作一次本地判断；概率为 10%。
- 触发后跳过接下来的两个用户回合。统计用户回合，不把同楼续写、多个群成员回复或 API 请求数算成新回合。
- 只决定“本轮触发／未触发”，不掷事件种类、吉凶、强度，也没有预设事件池。
- 触发时向主 RP 模型注入一次遭遇事实与叙事要求，具体意外由主 RP 模型结合已有上下文写出。
- 重新生成和新 swipe 复用同一用户回合的判断，不再抽取；续写仍属于同一轮，不重置冷却或新建遭遇。
- 缺少旧回合记录，不意味着需要补抽。首次启用、打开 APP、重载聊天都不追溯触发。
- quiet、impersonate、dry-run 和非主 RP 的消息投影不创建遭遇回合。

依据：`modules/tavern/shared/runtime-events.ts:40`、`modules/tavern/app-src/runtime/run-once.ts:151`。旧版把触发事实绑定用户消息，见同文件 `:2398`；这是保留用户楼层归属的原因。

同一回复因检定发生多次续写时，遭遇事实仍指向该回复的一次事件。提示词依据已有正文接着写，不把每次请求当作又一次遭遇。程序保证不重复抽取；模型是否自然遵守叙事要求属于模型质量验收，不由触发记录假装证明。

### 2.3 请求与费用

Dice 本身对无检定聊天不增加模型请求；随机遭遇判断也不额外调用模型。一次检定通常使原回复增加一次主 API 续写，两次检定通常增加两次。

这不是“费用只增加一小段正文”的承诺：续写会重新发送上下文，注入的规则也占 token。实际费用取决于上下文、输出长度和供应商计价，不能把请求次数直接说成费用倍数。已有探针的请求数量和证据范围见验证报告。

## 3. 功能所有权与目录边界

首版业务集中在 `modules/xiaobai-os/apps/dice/`，通过 APP module 接入。下面表示职责分区，只有出现实际实现时才建文件，不先搭空骨架：

```text
apps/dice/
  descriptor.ts / module.ts / production-module.ts
  partition.ts              当前聊天的两个开关
  domain/                   检定规则、遭遇规则、消息记录的不变量
  application/              设置命令、检定闭环、遭遇回合决策
  protocol/                 JSON 契约、领域提示词、结果与遭遇资料投影
  host/                     酒馆事件、续写、保存核实、消息展示与清理
  ui/                       APP 页面、图标和自有样式
```

- `domain` 不读 DOM、酒馆全局对象或 OS Store；随机源作为输入依赖，方便验证真实规则。
- `application` 编排自有规则；运行身份和取消状态只留在当前运行内。
- `host` 把酒馆的消息、候选、保存与生成事件适配给应用层，不承担难度和冷却规则。
- `protocol` 不导入宿主对象；只把已经核实的规则、请求契约和本次数据提供给主模型。
- UI 只展示确认状态和操作反馈，不拥有另一份开关、骰点或冷却状态。
- 不 import `modules/tavern` 的运行时、数据库或状态模型；旧代码用于行为对照，不成为运行依赖。
- 不复用 `domains/game/games/dice-bluff.ts`。大话骰是独立游戏，其状态和本功能的剧情检定不是同一领域。

注册仅涉及：Dice module／partition、Host catalog 与生产组合、Shell catalog／launcher／懒加载入口，以及现有生成拦截分发器中的一个自有注册。首版不依赖 Agent、Economy、Maintenance 或 World Capability，不把 Dice 业务搬进 Kernel。

依据：`modules/xiaobai-os/kernel/app-registry.ts:20`、`modules/xiaobai-os/host/production-composition.ts`、`modules/xiaobai-os/shell/app-catalog.ts`、`shared/common/generate-interceptor.js:14`。

## 4. 数据归属与保存

### 4.1 唯一事实来源

| 数据 | 所有者与位置 | 为什么持久化 | 生命周期与删除 |
| --- | --- | --- | --- |
| 两个功能开关 | Dice 自有 sidecar `dice` 分区 | 用户的聊天偏好需要跨重启保留 | 按聊天保存；清理 Dice 时删除分区 |
| 本轮遭遇判断 | 用户消息的 `extra.xiaobaiOsDice` | 刷新、失败重试、重生成不能重新抽取，触发提示和冷却需要恢复 | 跟随用户消息；删除该楼即删除；显式清理 Dice 时移除字段 |
| 已执行的检定结果 | AI 当前候选的 `extra.xiaobaiOsDice`，与宿主 swipe 存档同步 | 已发生的随机结果不能因刷新、续写失败或切换候选而改变 | 跟随该候选；删除候选即删除；显式清理 Dice 时移除字段 |

开关分区只保存当前格式版本和两个布尔值；打开页面、两个开关均未启用时，不为默认值主动写 sidecar。

遭遇记录保存已经作出的判断，包括未触发。负结果不是持续运行状态：它表示这个用户回合已经决定过，不能在重试时反复抽直到成功。冷却由此前两个用户回合的触发记录推导，不保存第二个冷却计数器，也不保存未展示的随机采样值。

检定记录保存请求含义、实际骰点、当时的难度／判定结果和正文定位信息。结果卡片、续写结果资料都从它投影，不从 DOM 反向读事实，也不在 sidecar 再存一份骰点历史。

这限定了本 APP 对 Kernel 文档中“业务事实在 sidecar”的使用方式：独立 APP 偏好在 sidecar；附着于宿主聊天、必须随消息与候选一起进退的执行记录在消息中。不能以此为由把状态栏或世界文档搬回聊天 metadata。现有商店消息收据可证明宿主附属记录这一存储方式已被使用，但不复用商店收据的类型或语义，见 `apps/shop/host/message-receipts.ts:6`。

宿主要求在当前消息 `extra` 和活动 `swipe_info[swipe_id].extra` 间同步。它们是同一候选的宿主工作副本与存档，不是两套可独立更新的 Dice 历史；同步集中在 Dice 消息适配器中。不能把 `swipe_id` 或消息数组下标单独当作跨聊天永久身份。

### 4.2 只保留在运行内的状态

生成 token、取消标记、聊天／候选捕获、待续写队列、正在写入的候选、错误对象、重试按钮状态、待注入 Prompt、DOM 节点和流式显示缓冲都不持久化。

不增加 `pendingRoll`、`continuationQueued`、持久锁、全局楼层索引或另一份“最后处理到哪一楼”的游标。刷新可以恢复已确认事实，但不会自动恢复请求链。

### 4.3 保存失败与确认

同楼闭环顺序为：

```text
当前生成完整结束
  → 核验请求、聊天和候选仍有效
  → 本地只投一次，形成消息保存候选
  → 保存取得确认，结果未知时核实该候选的正文与 Dice 记录
  → 注入已保存的结果
  → 等宿主真正空闲后，原生 continue
```

宿主 `getContext().saveChat` 指向 `saveChatConditional`，后者存在等待超时直接返回、捕获错误后不向调用方抛出的路径。因此不能把 `await saveChat()` 返回当成保存确认。依据：SillyTavern `public/scripts/st-context.js:154`、`public/script.js:9354`。

现有 OS 的 `host/sillytavern-chat-save.ts:20` 已封装宿主聊天 HTTP 保存协议，并在 `:52` 核对成功响应，返回 confirmed／failed／unconfirmed；metadata 与 Messages 都已使用。正式 Dice 复用这个公共入口，不另造保存器，也不在 confirmed 后无理由再次下载整份聊天。

保存结果未知时，Dice 才按捕获的单聊／群聊 binding 读回，核对目标候选正文与 Dice 字段；仅核对内存对象不算落盘确认。读取协议可参考 `storage/sillytavern-chat-metadata.ts:104`，但该接口目前只投影 metadata，不能声称它已经提供骰点保存核实。公共保存确认不代替宿主收尾和当前目标检查，迟到的成功不能恢复已经取消的续写。

- 明确失败或结果未知：停止后续自动请求，保留本页同一骰点候选，提供核实／重试保存；不重新掷骰。
- 读回发生冲突：不覆盖第三方或宿主的新正文，不强制保存整份旧聊天快照；提示用户检查当前消息。
- 已保存结果、续写失败：显式重试重新发送同一结果，接在同一候选后面。
- 刷新后只恢复服务器上实际保存的事实。若骰点从未确认落盘，不能承诺恢复已经丢失的内存随机数，也不能静默重新掷骰冒充恢复。

遭遇判断同样先保存、核实，再用于主生成。判断未确认时暂停这次依赖它的生成并提示保存问题，不能默默重抽或以“未触发”掩盖保存失败；本页重试复用同一判断。未触发结果也只保存一次，后续读取不再写文件。

消息保存与 sidecar 不是一个事务。不为每次掷骰同时更新 sidecar；设置保存未确认时也不提前启用对应玩法。读取核实增加的是宿主存储请求，不是模型调用。

## 5. 主聊天协议与生命周期

### 5.1 Tagged JSON 边界

使用 Dice 自有的 `<xb_action_check>` 标签包装一个 JSON 请求；采用一套严格的当前格式，不同时保留原生工具和若干历史 JSON 分支。

请求保留旧版的 `action`、`stat`、`difficulty`，以及可选的 `character`、`stakes`。难度使用第 2 节的五档名称，不允许模型提供骰点或任意修改 DC。正文位置由“写出尝试、在检定处停止”的输出顺序确定，不让模型额外填写 `insertAfter` 来猜插入位置。

仅在 OS 与行动检定开关均开启时，处理当前真实主生成新收到的完整请求：标签完整、JSON 合法、字段符合契约，并位于这次输出的末尾。代码块、引用的示例、用户输入、历史文本和推理区内容不能被当作实际请求执行。重复接收同一完成事件不再执行；重载和普通消息渲染不会启动解析执行。

截断、非法 JSON、同一次返回包含多个请求、闭标签后仍有非空正文等情形，不修补成可执行调用，不投骰、不自动发“修复 JSON”请求；在所属回复上显示可理解的错误，保留用户通过酒馆编辑功能检查原文的能力。程序只验证这些结构条件，不假装能够自动判断标签之前的叙事是否已经暗示了成功。

合法请求执行后，将已消费的协议块从该候选正文中移除，保留检定前正文，并记录卡片位置。清理后的正文、骰点记录和活动 swipe 组成同一个聊天保存候选；保存核实前不开始续写。持久化的是骰点事实与定位信息，不是卡片 HTML；后续正常聊天不会再次读到这段已消费的请求。

正式请求 schema、解析器和用于模型的字段说明同属 `protocol`。本文不提供未经解析器测试的可复制模型示例；施工时每个示例必须通过同一公开解析入口执行。

### 5.2 提示词分工

不创建新的主模型身份，不覆盖角色卡或用户预设。模型说明默认英文，叙事语言跟随用户当前聊天。

| 层 | 应提供的内容 | 事实依据／设计约束 |
| --- | --- | --- |
| 检定领域说明 | 哪些有风险且未定的行动需要检定；先写尝试，结果出来后衔接叙事；首版无角色数值加成 | 旧 `action-checks.ts:75`、`:359`；本文第 2.1 节 |
| JSON 契约 | 标签边界、字段含义、必选／可选、五档难度、一次一个请求、结束当前输出 | 旧 `action-checks.ts:250`；本稿新增的运输约束由正式解析器证明 |
| 检定结果资料 | 当前候选中按顺序已经执行的请求、骰点、DC 和判定；这些结果已经确定 | 旧 `action-checks.ts:311`；本文第 4 节 |
| 遭遇领域说明与事实 | 当前回复的一次突发情境，符合场景和人物；衔接已经写出的部分，不把资料文字写进剧情 | 旧 `runtime-events.ts:49`；本文第 2.2 节 |

字段限制只在契约说明中定义，领域块不重复抄 schema。规则文本不进入持久化消息记录；记录保存数据，运行时产生 Prompt。注入文字作为资料安全处理，不把行动文本当宿主宏、HTML 或新的系统指令执行。

通过现有生成拦截分发器和自有的扩展提示词键接入，使用 SYSTEM／IN_CHAT、D1、`scan=false`，不替换全局 Generate，也不覆盖其他 APP 的注入。当前位置依据：`host/sillytavern-runtime-adapters.ts:17`；旧遭遇同样采用 D1。

请求组装完成后清除本次注入；后续 continue 从当前已保存记录重新投影。取消、切聊、关闭相关功能或停用 OS 同样清除自有注入，不能将骰点结果留给无关请求。正常后续回合不重新注入全部骰点历史，已完成的叙事仍由聊天正文承载。

### 5.3 宿主完成、停止与候选

- `GENERATION_ENDED` 不等于流式处理器和保存已经结束。自动续写必须等待宿主真正可接受下一次请求，且再次检查原聊天、原候选与取消状态。
- dry-run 只用于宿主计算，不创建、替换或取消真实检定运行。
- 同时识别非流式续写完成的 `appendFinal` 与流式的 `continue`。
- 用户停止后不再投骰或排新续写；停止前已确认保存的骰点仍保留。
- 生成新 swipe 时清除宿主可能复制过来的 Dice 工作字段；旧候选的记录留在旧候选，不能让新答案继承旧骰点。
- 切换候选只读取和显示，不产生请求、不重新投骰。
- 编辑影响检定正文定位时，不猜测它应该迁到哪一句：已发生结果仍可作为该候选的附属记录查看，但失去可核实接续位置时不自动续写。
- 重载后允许对仍然匹配的最后一条 AI 候选显式“沿用骰点续写”；不持久化或自动恢复“正在重试”的状态。

以上宿主差异的源码位置和有限实测见续写验证报告，特别是 `public/script.js:3477`、`:4240`、`:6660`、`:10061`。

### 5.4 OS 生命周期与群聊

Dice 玩法属于聊天后台运行，不属于 APP 页面前台任务：切换 APP、关闭 OS 窗口不取消已启用玩法。关闭对应功能、停用 OS、切聊天会使旧的自动处理与续写资格失效；不能因此中止另一个 APP 或用户自行发起的无关请求。已经发给主 API 的请求是否停止，仍尊重宿主的停止操作。

停用不等于删历史。OS 启用而功能开关关闭时，既有记录仍可显示；整个 OS／插件卸载运行后不保证继续显示自绘卡片，重新启用再按记录恢复。不开一个脱离 OS 总开关的常驻骰点服务来维持外观。

群聊的遭遇判断仍绑定用户回合，只抽一次；其事件指令绑定这一轮首次实际参与的 AI 回复，不能给每个群成员各触发一个意外。归属由该用户消息后的首个主 RP AI 楼层确定；该楼尚未建立时只在本次运行内捕获成员，保存后从实际聊天恢复，不另存一套群聊轮转状态。该成员的后续检定续写继续属于同一回复。必须验证群聊成员选择、轮转和 wrapper 生命周期，不能仅等待一个全局空闲标记后让另一成员接着写。

## 6. UI：APP 设置与聊天附属展示

### 6.1 APP 页面

页面主角是当前聊天的两个开关，沿用 OS 导航、字体、控件和深浅主题：

- 行动检定：简短说明模型提出检定、本地投骰、按结果续写。附近说明检定会增加主 API 续写请求。
- 随机遭遇：简短说明偶发事件，以及固定的 10% 概率和两回合冷却。
- 行动检定开关附近固定说明：“使用 Roll 点时，请关闭酒馆设置中的‘自动续写’。”

不再增加 APP 总开关、统计卡片、欢迎语、骰子装饰动画或未来功能灰色占位。当前聊天范围用一处简短标识说明，不给每个控件重复加说明段落。

开关保存时表现为保存中；确认后才按新值运行。失败保留已确认值，错误出现在操作处。存储未确认沿用 OS 文件恢复，不在 Dice 里复制一套 sidecar 保存恢复系统。

### 6.2 行动检定卡

卡片属于 AI 的当前候选，放在尝试和后续结果之间。显示检定项目、必要的行动描述、D20 骰点、DC 与成功／失败／大成功／大失败；不能只用颜色区分。首版不显示不存在的属性加成。

卡片是已保存事实的视图，渲染本身不投骰、不写文件、不发请求。主回复失败时，错误和“沿用骰点续写”入口属于这条回复，不要求用户打开 APP 才能恢复；没有重掷按钮。

### 6.3 随机遭遇提示

保留旧版“用户发言之后、AI 回复之前”的阅读顺序，但普通酒馆实现为用户楼层内部的附属区域：

```text
第 12 楼 · 用户
  我推开酒馆的门。
  🎲 随机遭遇已触发     ← 第 12 楼的附属 UI

第 13 楼 · AI
  门后突然传来……
```

只对触发回合显示，不给未触发或冷却回合加灰色提示。此标记表示“本轮的遭遇指令已触发”，不是程序已经识别并确认了 AI 正文中的某个事件。

- 不向 `chat` 数组 push 一条消息，不调用新增系统／旁白消息来占楼。
- 挂在所属用户 `.mes` 容器内、正文区域之后；不在 `#chat` 根部留下独立且无法随楼层清理的兄弟节点。
- 提示本身不写入用户 `mes` 正文，不作为历史消息送给模型。需要给模型的遭遇指令另走 Prompt 注入。
- 刷新、载入更早消息、消息重绘时从记录重建，重复事件不会重复挂载。删除用户楼层时自然移除。
- 文字、间距、横线与主题只影响显示，不依赖模型输出 HTML，也不需要从 AI 正文猜一个插入位置。

旧版位置依据：`modules/tavern/app-src/components/chat/TavernConversationPanel.vue:560`。普通酒馆 `.mes[mesid]` 定位及重绘依据：`public/script.js:2492`；现有扩展添加楼层按钮的实例见 `modules/story-summary/story-summary.js:2079`。这些是接入可行性的源码证据，不是本卡片已经完成浏览器验收。

### 6.4 流式协议隐藏的工程门槛

完整 `<xb_action_check>` 开标签出现后，由显示正则隐藏此标签及其后的协议 JSON；此前半截标签允许短暂显示。用户明确不要求首字符零闪现，不为普通 `<` 另建处理。不能等整轮完成才删 JSON。原始响应解析与显示过滤分开，不能为了隐藏而丢掉待解析数据。

用户已同意自动维护原生全局 `markdownOnly`、AI placement 正则，不再要求它是非持久化挂钩。固定 ID 为 `xiaobai-os-dice-action-check-display`，所有者为 Dice；采用持久配置是宿主当前正则注册入口的约束，不是保存运行任务。它不负责执行检定、不改变原始消息、不启用其他聊天的玩法。

已验证正常维护不写设置、误删下次检查补回、禁用修复、关功能不补回、只移除自有规则、宿主 converter 重建和部分 Markdown 保护；细节见施工记录。规则保持有效时无需刷新整聊／设置 UI，既不请求模型也不逐字执行维护。不能偷偷重启用户禁用的整个正则扩展。

生成期间在酒馆原生 UI 删除规则会触发重载，实测打断了未完成回复；补回规则不等于能恢复该轮。需在说明中提醒生成时不要编辑／删除自管规则，不扩大为宿主删除协调器。完整开标签显示边界、全局正则持久化和不兼容酒馆自动续写均已确认，不再是待批准事项。

## 7. 分支、导入、清理与真实兼容范围

### 7.1 聊天生命周期

分支聊天沿用 OS 现有机制取得独立 sidecar，复制两个偏好；骰点和遭遇记录只随宿主实际复制过去的消息／候选保留。未来消息的遭遇不参与子线冷却，父线与子线各自继续。Dice 不另建全局事件表来做第二次分支复制。

消息删除、候选删除和聊天删除由宿主携带附属记录一起处理。Dice 分区只剩两个偏好，不需要用消息前缀回滚 sidecar。导入能保留 `extra` 的当前酒馆聊天时可恢复记录；只有纯文本的导入不能从看似相同的文案猜出历史骰点。

记录在加载／导入边界按当前格式解析；缺失表示没有本功能记录，不表示需要补抽。坏记录给出局部错误，不改其他消息、不覆盖未知字段、不执行模型请求。

### 7.2 删除路径与失败处理

关闭开关不清数据。用户显式清理 Dice 数据时，策略为：丢弃两项偏好、骰点附属记录与遭遇判断，保留已经生成的聊天正文和其他 APP 字段；不把清理等同于回滚剧情。

按已明确的聊天范围执行：先关闭两项功能并确认保存，再清除消息及全部候选中的 `extra.xiaobaiOsDice` 并确认聊天保存，最后删除 `dice` 分区。消息清理和分区删除不是原子操作，任何一步失败都如实停止；重复清理应安全，不能为过程增加持久化清理锁。

现有 `AppDataCleanupContext` 只提供 `removePartition`，并不能清理宿主消息。Dice 必须自带消息清理步骤，在其清理入口组合两项操作；不能只删分区就声称已经清干净。批量卸载需先明确聊天范围并用一次性清理处理其中的 Dice 字段，不能未经选择扫描改写用户所有聊天。

完成数据策略后，注销事件、拦截器、Prompt 键与显示资源，再删除 Dice 目录和注册项，重建对应产物。不留自己的旧字段兜底、旧协议壳或后台复活逻辑。

全局自管正则与单聊数据生命周期不同：仅清理某聊天时不删除其他聊天仍需的显示规则。整体卸载时删除上述固定 ID 的规则；若先直接删除插件目录，需由用户在酒馆全局正则中删除“小白 OS · 行动检定显示（自动管理）”。只删除自有规则，不清空正则列表。

### 7.3 兼容范围

需要支持的是现行 SillyTavern 消息／swipe／群聊／保存协议、浏览器和 WebView、主模型供应商输出与现行 OS sidecar／聊天文件格式。JSON 路径不要求模型提供原生 tool calling 能力。

酒馆 native-tools 开关开启不等于 Dice 改用原生工具；已有探针只证明该开关不排斥 JSON，不能据此承诺与其他原生工具调用的完整混用行为。相关组合需要作为宿主集成场景验证。

不迁移小白酒馆数据库、测试探针 `rollProbeResults` 或未上线旧实现。未来若格式真正发布且需要升级，先冻结实际旧格式及 fixture，再在升级边界转换；首版不预埋历史兼容层。

## 8. 未来扩展，不预埋实现

### 状态栏

未来仍可放在同一个 APP，但状态文档、属性编辑、属性更新规则属于自己的部分。检定只读取当时可用的角色属性，保存实际执行时的判定依据；不拥有第二份状态文档，不让 UI 上尚未保存的属性影响骰点。

届时才引入属性读取与 D100 路径。首版不增加空 `status` 分区、属性 provider、虚构角色 ID 或永远为 null 的字段。

### 世界与总结增强遭遇

“本轮是否触发”和“触发后用什么素材”分开。未来丰富素材不应牵动骰点幂等、冷却和楼层 UI。

- 世界已有自有只读入口 `WORLD_CONTEXT_CAPABILITY.readCurrent(chatIdentity)`，见 `apps/world/context-capability.ts:11`；正式接入时消费它，不直接读写 World 分区。
- 当前 OS 背景捕获已通过 `host/prompt-context/adapter.ts:13` 读取剧情总结事件，并传入截止楼层。后续按真实需求从既有捕获边界取资料，不在 Dice 新建摘要库，也不拿没有截止位置的整份未来总结污染分支。
- 增强版只在需要时读取可用资料，区分公开世界消息和剧情已知事实；没有世界或总结时保留基础遭遇能力。

这版不注册上述依赖、不等待后台总结、不新增 Agent 调用，也不建立一个提前抽象的通用规则引擎。

## 9. 最少必要测试与验收

测试保护可观察行为和数据安全，不以源码 includes、函数名、文件位置或 Prompt 句子快照证明实现存在。

| 最低成本层 | 保护的契约 | 需要捕获的真实故障 |
| --- | --- | --- |
| 领域单测 | D20 难度、临界成功／失败；遭遇概率边界与两回合冷却 | 比较方向、边界、冷却单位错误；用注入的确定随机源验证，不做不稳定的抽样统计测试 |
| 协议单测 | 合法完整请求可执行，截断／引用／多请求／错误字段不能执行；结果投影一致 | 误识别正文为工具、解析残片后误投骰；正式模型示例走相同公开输入输出 |
| 应用与宿主适配集成 | 一次执行、保存确认、失败沿用原结果、候选隔离、停止／切聊失效 | 宿主吞保存错误、新 swipe 继承旧字段、事件重复、迟到完成污染新聊天 |
| 随机遭遇集成 | 一用户回合一次决策、重生成不补抽、续写不消耗冷却 | 模型请求次数代替用户回合计数；群成员各抽一次 |
| 真实酒馆＋模拟供应商 | 请求数、结果进入续写、同楼接文、流式隐藏、保存重载、群聊成员归属 | 单测不能证明的原生生成时序、显示入口和文件持久化行为 |
| 正式组件浏览器检查 | 两开关操作、检定卡与附属提示、重绘／删除、长文本、窄屏／深浅主题、焦点与可访问名称 | 文字泄漏、提示重复、卡片串候选、溢出或操作不可达 |

完整 OS 联动至少检查：关闭窗口仍能运行、停用不再发请求；商店有限效果不因 Dice 同楼续写重复扣次数；地图／任务／世界注入不丢失、不串请求；私人信息等消息投影不被当成遭遇新回合。对已有模块只修被复现的契约冲突，不借机改造无关运行时。

真实模型另验：能否稳定停在检定边界、遵守已确定结果、连贯续写，以及遭遇是否自然。模拟供应商只能证明协议，不证明模型质量；真实付费调用需使用用户明确授权的配置与范围，不默认由测试启动。

正式代码落地后运行有针对性的测试，再执行 `npm run test:xiaobai-os`、`npm run lint:xiaobai-os`、`npm run build:xiaobai-os` 和 `git diff --check`。文档阶段不靠重跑旧测试或构建宣称新功能已验收。
