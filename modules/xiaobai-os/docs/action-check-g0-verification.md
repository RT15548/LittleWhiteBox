# Dice 行动检定：G0 宿主接入施工记录

日期：2026-09-14。本文仅记录 G0 历史实验；当时尚未注册 Dice APP。后续正式实现与注册已完成，当前结论请见 [G2–G5 施工验收](./action-check-g2-g5-verification.md)，下文保留历史实验的原始边界。

## 结论

用户随后明确：完整 `<xb_action_check>` 开标签出现后才隐藏，半截前缀不处理；专用标签本身可以接受。因此下文 `<` 冲突只保留为已放弃的首字符隐藏实验，不再阻塞施工。G1 已开始；完整功能仍未交付。按[施工方案](./action-check-implementation-plan.md)验证的历史结果如下：

| 边界 | 实测结果 | 当前结论 |
| --- | --- | --- |
| G0-A：非持久化显示挂钩（历史实验） | 当前 converter 的扩展可隐藏分块协议，但重建后失效；扩展输入缺少消息角色／楼层，直接过滤同时影响相同内容的用户消息 | 已放弃；用户已批准改为自管全局正则 |
| G0-A：自管全局显示正则（原候选） | 正常检查零写入；修复、清理、逐字流式及 converter 重建通过所列用例；补测代码／引用误过滤已修正 | 首字符隐藏会吞普通 `<`；用户已明确不需要此要求，正式规则已移除此匹配 |
| G0-B：公共保存边界 | 正常确认、HTTP 400／503、写入后丢响应、宿主保存忙、切聊后迟到确认均取得可区分结果 | 所列保存边界通过；不是 Dice 失败恢复功能已实现 |
| G0-C：两个群成员连续回复 | 在下一位成员的 drafted 事件内暂借原成员身份完成续写，再恢复下一位；流式／非流式均保持原楼、成员顺序及保存结果 | 双成员成功路径通过；完整群聊错误／取消链仍待正式实现验收 |

这不是 JSON 路线失效，也不需要接管主 API。原来的“不写显示配置”约束已由用户明确调整；没有全局替换渲染器或闪现后删 DOM。酒馆自动续写仍是已接受的不支持组合，不重新列为阻塞。

## 追加实验：自管正则

只在隔离设置内安装固定 ID `xiaobai-os-dice-action-check-display` 的 AI／仅显示规则；不修改真实用户设置。候选逻辑仍在忽略目录，未作为正式实现注册。

| 场景 | 实际观测 |
| --- | --- |
| 连续检查 100 次，规则有效 | 设置写入 0 次 |
| 缺失后检查 | 补回同 ID 规则，写入 1 次 |
| 自有规则被禁用 | 检查后恢复启用 |
| 功能关闭且规则缺失 | 不补回，写入 0 次 |
| 清理 | 只移除自有 ID，另一条用户规则仍在 |
| 逐字输出正式标签 | 三种场景均只见普通正文，没有标签、JSON 或部分标签；原始输出完整，模型请求各 1 次 |
| 标签转义＋自动 Markdown 修正＋流式淡入 | 同上，未关闭这些设置规避问题 |
| 重建 Markdown converter | 同上；另一条把 `Visible` 改为 `DISPLAY` 的用户规则仍有效 |
| AI／用户相同原文 | 只过滤 AI，用户原文显示保持不变 |
| Markdown | 围栏、单／双反引号、引用、缩进代码及普通比较符号的初始七例保留；补测混合反引号及引用惰性续行先失败，修正候选后通过 |
| 末尾普通 `<` | `The symbol is:\n<` 在原生格式化中可见 `<`，加候选规则后消失；开关标签转义均复现 |

最后一项属于已放弃的过度要求：纯显示正则无法区分末尾普通 `<` 与标签首字符，但用户明确不需要在此时识别。当前采用完整开标签作为边界，所有更短前缀都不匹配，保留普通符号；不再将它当成产品阻塞。旧结果不改成新规则的验证证据。

候选修正仅涉及代码片段精确反引号宽度、引用惰性续行保护、部分前缀仅匹配全文末尾；没有变更正式协议或生产代码。JSON 字符串内相似标签的样本作为真实请求被整体隐藏是预期结果，不把其 `preserved:false` 误记成正文误删；正式解析器仍待实现验收。

### 开销范围

修正后的候选在本机浏览器测得：201 条规则列表、1000 次检查，平均约 0.0073 ms／次；108091 字符正文、100 次过滤，平均约 0.747 ms／次。先前候选约 0.0096 ms 与 0.613 ms 的结果另行保留。测量只说明这些输入下的开销，不是移动 WebView、任意 Markdown、整聊重绘或正式卡片的性能承诺。

### 生成途中从原生 UI 删除

手动加载宿主原生正则 UI（隔离配置仍禁止自动加载第三方扩展），打开自有规则的删除确认框；开始本地分块响应，在未结束时点击“确定”。

实际结果：规则删除，宿主立即重载聊天；原先可见的 `Visible attempt.` 消失，只剩初始问候和用户消息。控制台在 `script.js:3620` 报 `Cannot read properties of undefined (reading 'mes')`，`streamingProcessor` 仍存在。总请求 1 次，没有投骰或补发模型调用。下一次显式检查补回规则、写设置 1 次，但不恢复被重载打断的回复。

因此“误删补回”只承诺后续检查恢复规则，不承诺在途生成无感恢复。使用说明须提醒生成期间不要编辑／删除自管规则；不为此改造宿主删除或流式处理器，也不增加逐 token 维护。该实验没有运行正式 Dice，所以不能算作 Dice 取消／恢复功能已通过。

## G0-A：非持久化入口的历史实验

### 当前实例的 Showdown 扩展

在 `st.converter.addExtension` 注册 language filter 后，以正式 `<xb_action_check>` 标签逐字符流式返回；同时开启标签转义、自动 Markdown 修正、流式淡入。

帧采样只有正常正文 `Visible attempt.`，原始消息仍完整保留请求；说明这个位置可以在 DOM 写入前过滤，不需要破坏解析原文。对实例执行 `removeExtension` 可移除过滤。

但调用宿主真实的 `reloadMarkdownProcessor()` 后，同样的生成逐帧出现 `<`、`<x`、`<xb`，最后出现完整 JSON。宿主确实创建新的 converter；不是现有实例上的配置更新。设置中的 Markdown 排除字符串修改就会走这条路径，见宿主 `public/scripts/power-user.js:3276`。

还以相同原文分别调用宿主 AI／用户消息格式化。filter 接收到的处理文本、`mesForShowdownParse` 原文及 options 完全相同，两者都被简单过滤为正常正文。这个入口没有传入 `isUser`、`messageId`、`isReasoning`，不能只凭相同原文可靠判定归属。此实验只否定该接法，不声称所有可能的宿主改造都无法实现。

源码边界：`public/script.js:1749` 的 `messageFormatting` 接收来源信息；`:1781` 起按来源执行正则；`:1880` 调 converter 时只传文本；`:520` 重建实例。正式文档不得继续把“converter 可加扩展”写成“已找到满足来源隔离和重建契约的挂钩”。

### 全局注册和正则对照

又验证了 Showdown 全局 `extension` 注册及默认 `extensions` 配置：普通新 converter 能使用它，宿主新 converter 仍不使用。原因是宿主构造时显式提供自己的 `extensions`，覆盖了默认值。全局注册与默认值均在实验结束恢复。

原生 `markdownOnly`、AI placement 正则作基础对照时，重建后仍能隐藏完整协议，用户相同内容不受影响；但该条规则确实会出现在 `JSON.stringify(extension_settings)` 中。现行正则来源及保存入口是 `public/scripts/extensions/regex/engine.js:102`、`:143`，没有在此找到独立的运行期注册槽。

当时的正则对照尚未验收代码／引用、部分标签、用户正则组合和开关生命周期；本轮追加结果见上文，不用新结果覆盖旧实验的失败事实。

### 用户随后已确认的调整

用户已接受 Dice 自动维护一条有固定归属、可清理的原生显示正则：只处理 AI 消息的 Dice 协议，不改已有正则，用户无需手工配置。它属于会随酒馆设置保存的配置，不再伪装成临时态。

生命周期已补入施工方案：启用／真实生成前检查，只有缺失或损坏才写入；关闭功能不补回；清理所选聊天不删除全局规则，整体卸载才移除；直接删除插件时须手动删除对应名称。请求执行仍只来自当前真实生成，正则不负责投骰、保存或请求模型。

该配置边界调整已获批准，隔离验证已实施，但生产实现尚未开始。没有替换宿主全局构造器、Markdown 子解析器或用户设置对象。

## G0-B：保存与完成边界

直接加载编译后的现有公共保存器，观察结果：

| 注入情况 | 返回／读回 |
| --- | --- |
| 正常宿主响应 | `confirmed` |
| HTTP 400 | `failed / chat_save_http_400` |
| HTTP 503 | `unconfirmed / chat_save_http_503`，不能武断当作绝对未写入 |
| 服务器完成写入后，浏览器丢弃响应 | `unconfirmed / chat_save_unconfirmed`；随后 `/api/chats/get` 读回本次 marker |
| 暂缓原生保存，`isChatSaving` 为 true 时调用公共保存器 | `failed / chat_save_busy` |
| 公共保存已派发，确认前切换隔离聊天 | 最终 `confirmed`，但原目标身份已不同 |

最后一项证明：保存确认和“还能续写原目标”必须分别判断。公共保存器的迟到成功是正确行为，Dice 仍需在异步边界核对身份，不能把取消责任塞进保存器。

真实流式群聊中，`MESSAGE_RECEIVED` 时 processor 仍存在；下一位成员 drafted 时 processor 与宿主保存均释放，此时公共保存得到确认，再发起原生 continue。非流式同样通过。回调没有在 `MESSAGE_RECEIVED` 内等待宿主完成，避免形成互等。

未宣称完成：正式 Dice 单聊完成屏障、超时／取消、保存冲突核实、重试按钮以及候选安装等，仍须 G2／G3 集成测试和正式浏览器验收。

## G0-C：群聊成功路径

对照实验中，第一位回复检定请求，第二位正常回复；等 `GROUP_WRAPPER_FINISHED` 时，第一位已不是最后一楼。因此全局忙闲等待不能作为群聊同楼续写策略。

可用的薄接法利用宿主 `await GROUP_MEMBER_DRAFTED`（`public/scripts/group-chats.js:1060` 附近）：

1. 接收第一位的完成候选，及时返回。
2. 下一位 drafted 时，上一轮 Generate 已返回，流式处理器与保存已释放；群聊 wrapper 仍忙。
3. 在这个被 await 的成员边界内，暂设原成员身份，保存骰点，取得明确确认。
4. 以同一 wrapper 的 AbortSignal 调 `generate('continue')`，D1／SYSTEM 注入实验结果。
5. 原楼续写完成后清除注入、恢复下一位身份，返回宿主轮转。

流式／非流式均得到：一条用户消息、第一位同楼“尝试＋结果叙事”、第二位一次正常反应。实际模型请求为 3 次，只有第 2 次带结果资料，第 3 次没有遗留结果注入；第一位消息和活动 swipe 保存同一份结果，重新加载一致。

这里的 `isGenerating()` 仍为 true，因为它包含群聊 wrapper 标记。不能在已验证的成员边界继续等待它变 false，否则仍会互等；也不能据此在任意忙碌时插入请求。

不把这个成功探针直接搬进生产：连续多次检定、最后成员收尾、停止／切聊、成员删除、其他事件监听器及保存失败后如何阻止错楼恢复，仍需正式适配器与错误链验收。本次没有改写群聊 wrapper、维护另一套成员队列或承诺完整群聊支持已经交付。
