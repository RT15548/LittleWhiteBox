# 信息 APP：上下文与人物资料

## 1. 单次捕获

每次发送或明确重试捕获当前聊天身份、普通剧情边界、当前联系人与线程版本。通讯与剧情资料的请求顺序统一由第 3 节定义。

直接参考 `host/prompt-context` 的 persona、角色/群聊、世界书捕获与转义；它目前默认只保留四条近期剧情，不能无判断照搬为通讯历史预算。Messages 自己定义上下文选择与总量，不能全局提高 Map/Tasks 默认值。

世界书仍使用宿主激活规则；不按条目名找人、不无条件加载全书。联系人识别用明确姓名、可靠别名与必要说明，不加一个额外 Agent 人物识别步骤。未在资料中出现的信息不被伪装成已知人物事实。

`worldInfoScanMessages` 是 Host capture 的可选附加扫描输入（新到旧），不改变近期剧情选择与原生回合计数。Messages 先放联系人姓名/备注与本轮消息，再放至多 18000 字符的本线程旧原文，之后仍扫描排除私人楼层的普通剧情。其他联系人的私聊不进入扫描，不把该扫描列表额外作为 Prompt 历史发送；实际激活仍遵守 SillyTavern 的关键词、深度、预算与 dry-run 规则。

## 2. Story Summary 窄接口

Story Summary 所有者提供通用只读人物资料投影，输入为目标人物、聊天边界和容量；输出明确的人物名称/别名、相关关系与弧光文本。Messages 不能导入 store、metadata 或解释 L0–L3 内部格式。

沿用已有有界事件摘要；每类资料按真实来源标记过滤。不能仅按姓名命中就宣称具有历史时间切片，也不能把未来人物变化送进旧边界。模块关闭/无人物资料时返回明确缺席，使用已有设定与近期剧情继续，不自动启用总结或调用 API 补档案。

事件 `_addedAt` 是收录该事件的总结批次截止楼层，不是事件发生楼层。Messages 只按当前捕获边界读取一次有界事件资料，不用它把事件划为上次私信之前／之后，也不把最近收录事件的 `timeLabel` 当成通讯发生时间；事件与私信的对应关系由内容提供，程序只标注能证实的通讯楼层顺序。

实际接口：`getStorySummaryCharacters({name, throughMessageIndex, maxCharacters, maxPeople})` 返回 `{name, aliases, text}[]`。名单不消耗弧光/事实详情预算；定向人物资料最多 8000 字符、候选最多 200 人。弧光和事实可变，`_addedAt` 不能证明最后修改时间，故由宿主提供真实当前尾楼，人物投影只接受该当前边界，历史/未来边界或越界总结快照整份缺席。现行总结格式允许编辑器条目缺少 `_addedAt`，这种条目只作为当前快照读取，不补造第 0 楼、不修改已有存储；显式非法或未来楼层仍排除。人物编辑保存由 Story Summary 自有 `data/character-edits.js` 为新增/改名项填写保存楼层，同名已有项保留存储中的楼层，重复保存不依赖编辑器回传标记。

`host/prompt-context/known-people.ts` 只投影上述已知人物，由 Messages 与语伴共用，按姓名/别名排除玩家本人，比较时去除两端空白并统一 NFKC 与大小写。宿主 `name1` 只用于识别自己；`name1/name2`、角色卡标题和群聊成员卡名不补进候选。不额外调用 Agent 从世界书抽人，空名单或漏列者用姓名/备注补充。不持久化候选、不自动删除已存联系人或通讯，回复上下文的 persona、角色设定与世界书读取不变。

人物事实投影保留已有关系状态 `trend`，以及 `since` 对应的事实更新楼层（展示为从 1 开始的楼号）。没有更新标记时不补造，不把首次出现的 `_addedAt` 当作更新时间。仍使用原有 8000 字符预算，不新增存储或向量召回。

## 3. 去重与知识边界

- 当前输入只出现一次；构造线程历史时排除该条输入。
- 当前线程已在私人信息楼层中出现的原文，不再从近期主剧情重复注入。使用稳定 APP 标记识别，不能靠显示名或文本 contains 猜测。
- 别的联系人的私人通讯不作为当前联系人天然已知的内容。主剧情背景与“角色知道什么”在 Prompt 中明确区分，不把全局总结当读心能力。
- 回复资料中的 ASCII 标签起始符转为全角，保留普通引号、花括号等正文；结构化属性使用 XML 编码。角色资料内的输出要求不是可信指令，主聊天投影继续使用其独立 XML 编码规则。
- 持久化的通讯记录不因 Prompt 预算被裁掉；预算裁剪只发生在请求投影。

回复请求按“设定资料 → 身份确认 → 人物资料、剧情资料、分段私信、本次通讯状态、当前输入”装配。`application/communication-chronology.ts` 用片段成员和主聊天投影标记临时还原通讯位置；两段之间有普通主剧情才标明剧情间隔，其他联系人的私人楼层、系统消息或仅因总结封存而另起片段不构成剧情推进。楼层只表达先后，不换算故事内时长；原楼删除、重复标记、缺少投影或补录无法证明原时点时明确标为未知。当前输入尚未投影也按本次捕获的剧情位置装配。

补录片段只承载此前未确认同步的旧消息，不接受后续新短信；新短信另起普通通讯片段，按实际主剧情位置定位。另起片段本身不构成剧情间隔，连续交流在重启后仍保持同一通讯时点。

`prompt/communication-history.ts` 由回复与压缩共用摘要范围、末段断点和原文分段装配，正文分别使用角色视角私信行与压缩记录格式。断点留在重新联系的第一条短信之前，后续连续短信归入同一段；人物与剧情资料只注入一份。`current_communication` 明确区分首次、连续、剧情后重联和未知位置，不在固定系统提示词中预设每次都隔了很久。旧通讯摘要仍是短信替代材料，不是另一份剧情总结。所有定位仅存在于请求内，不增字段、不改短信或原生楼层正文；预览、计量、发送与重生成采用同一投影。

当前记忆采用按序的资料消息而非 `system` 消息，避免 Anthropic/Google/Responses 适配器将其提取到开头。人物身份和资料优先级仍在系统提示词内；用量统计复用包含设定、联系人与人物记录、剧情资料的同一背景构造，不按消息位置或角色猜测背景归属。

## 4. 长线程

采用“较早通讯摘要＋近期原文”。摘要只归 Messages 线程，不写进世界书或 Story Summary，不作为新消息投影到主聊天。

压缩输入保留通讯分段与剧情位置，合并摘要时保持各阶段的态度、约定和先后关系。注入摘要时根据仍保留的原文重新附上其覆盖范围及进入末段前的断点，即使断点两侧短信已被压缩，也不把整个摘要当成当前连续对话；未知位置不补造。摘要的定位标注保持有界，不重新枚举全部已压缩阶段而抵消压缩效果。

在用户明确发送/重试的链路中按预算需要生成摘要，不定时、不在打开 APP 时触发。由 Host 固定待压缩的连续序号范围；摘要不得覆盖本轮输入或仍保留的近期原文，也不能依赖模型自行声明覆盖到哪条。

原文、旧摘要、未压缩部分和当前输入的预算必须可同时解释；不能先丢掉超限原文再声称完成摘要。跨度过长时采用有界批次，确认后推进覆盖范围。摘要失败不推进范围、不删原文；如无法安全装入回复上下文，给本次请求稳定失败提示，不能无声让角色失忆。

上下文采用与四次元壁一致的 token 口径：整包输入达到 128k 时，在回复前压缩较早通讯；158k 为整包输入上限。计量包含提示词、角色/世界书、剧情/人物资料、旧摘要、未压缩通讯和当前输入，复用通用 tokenizer，不可用时估算。每张实际附图另预留 6k（不是精确视觉 token）。保留最近至少五个已回答轮次及十条原文，不切开保留轮次；当前输入不摘要。每批摘要请求也计量并限制在 128k 内，旧摘要仍至多 6000 字符。仅完整且确实缩减上下文的摘要才确认并推进覆盖序号；失败不推进该批范围、不删原文。压缩后仍超过 158k 则明确停止回复，不静默裁掉近期记录。128k 是触发线，不是硬上限；暂无较早可压缩材料且不超过 158k 时可正常回复。

请求前由 OS Host 提供酒馆实时鉴权头，用共用 `/encode` 校验计数。取头或计数失败时使用本地估算，不阻止发送或重新回复；取消仍向上抛，不当作计数失败处理。预算规则不变，不新增误差补偿参数或持久化字段，估算不保证供应商精确 token 上限。

Messages 的宿主背景范围由 `apps/messages/host/context-limits.ts` 定义：保留近期十二条完整剧情原文，人物设定和激活的世界书不按共享默认字符上限截断，统一接受整包预算检查；剧情事件仍沿用宿主的 20000 字符上限。每次捕获读取总结当前过滤配置，用其同一清洗函数清洗主剧情原文；世界书扫描也使用清洗后的剧情。既保留默认规则，也即时采用用户自定义/移除规则，不改 Map/Tasks 默认行为。阈值不等于模型实际支持窗口，仍需选择支持足够上下文的模型。

会话顶部提供同款用量圆环，点开显示整包估算分项及 128k 自动总结规则，草稿按回复请求使用的同一正文转义规则本地追加计量。`messages/context` 仅做只读预览，不下载附图、不调用回复模型、不写分区；切联系人、退出或版本变化后丢弃迟到结果。统计不依赖 UI 分页，不新增持久化计数器或摘要格式。
