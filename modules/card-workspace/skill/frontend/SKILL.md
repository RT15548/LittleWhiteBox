# 小白X卡片前端

前端是玩家读故事、看场景、做操作的地方，对应 CardFlow 设计方案里“呈现与操作”一层。推进方式与需要确认的事项按 ReadSkill builtin-card-files 的 CardFlow 原则判断；该技能也说明卡的设定、世界书、设计方案与写回。数值和结算读 builtin-state3，已有 2.0 卡读 builtin-state2。

## 先走一遍玩家的路

设计或检查交互时，沿着玩家的一轮游玩梳理：进入场景 → 读到当前处境 → 做出行动 → 看见回应与结果 → 继续游玩。局部修改只看受影响的环节。界面上放的是此刻发生的事和玩家此刻能做的事，不是变量清单。

入口也是场景设计的一部分：它让玩家知道进入什么、接下来能做什么。形式由题材与使用方式决定。承担主要游玩的界面，把正文、行动、输入和反馈接在一起；返回酒馆用于宿主设置等外围操作，而不是每轮读故事的必经步骤。

## 前端承担什么

| 职责 | 玩家怎样使用 |
| --- | --- |
| 正文展示 | 在聊天楼层里读正文、看插图；需要时提供本楼交互 |
| 辅助面板 | 游玩主体仍在聊天；面板补充状态或某项操作 |
| 一体游玩界面 | 在同一界面里阅读、行动、输入、查看结果；按需要接住重写、变量结算和图片操作 |

先定职责，再选择布局与挂载方式。全屏是布局选择，不代表要重写聊天系统。做一体界面时，先读[解铃会成品示例](<examples/jieling.md>)：它用场景入口进入游戏，正文与案头操作同屏，经营操作和图片操作也在界面内；门、双栏和配色属于这张卡，不是其他卡的固定模板。

## 消息与存档由谁管理

| 做法 | 怎样运转 | 卡要负责什么 |
| --- | --- | --- |
| 复用原生聊天 | 界面发送玩家消息、读取真实楼层与当前变量；酒馆保存消息和 swipe，小白X管理受管变量 | 显示真实楼层及变化，接入当前操作、生成状态和失败反馈；具体接法见[一体界面参考](<../references/xiaobaix-heavy-ui.md>) |
| 自行生成，使用小白X变量 | `callGenerate` 生成文本，变量接口提交结算 | 自己保存生成文本与回合对应关系；同一楼里多次点击不会自动变成多个可回退楼层 |
| 自行生成并存档 | 卡保存每回合的正文和状态 | 按聊天或存档隔离，负责刷新恢复、部分失败、撤销与删除 |

玩法沿用聊天时，优先复用原生聊天。独立生成和存档用于确实需要独立回合的玩法，不由全屏与否决定。开场楼网页在编辑、swipe、换聊天或刷新时会重建，页面里的 JS 变量不是存档；浏览器本地存储也不随卡导出或随删楼回退。

## 选择挂载方式

| 需要什么 | 做法 |
| --- | --- |
| 正常文字聊天 | 无需附加前端；需要变量时只做初始化与提示词 |
| 本楼静态排版 | 显示正则替换成酒馆净化后的 HTML，无脚本 |
| 本楼网页与交互 | 显示正则替换成 HTML 代码块，由小白X渲染为楼层 iframe |
| 跨楼层主界面 | 角色循环任务挂载常驻界面，负责更新与清理 |

正文格式需要正则配合时，用卡自己的标签，检查预设是否改写或剥掉它。标签不嵌套同名块，生成中断时未闭合的正文仍可阅读。楼层 iframe 在生成结束后才渲染，流式过程中显示原文。

旧楼是当时发生的事；当前操作台与历史正文分开。数值从变量读取，不让模型每楼重抄全部状态。只在最新楼展示的正则使用 `maxDepth: 0`。

图片可自备、运行时生成或混合使用。固定素材用[随卡图片](<portable-images.md>)装进卡，前端可按变量状态选择图。聊天已有图片时，在自定义阅读器里复用图片卡及其操作，接法见[一体界面参考](<../references/xiaobaix-heavy-ui.md#host-features>)；独立绘图和语音见[媒体接口](<../references/xiaobaix-capabilities.md#media>)。

## 在哪里执行代码

| 位置 | 适用寿命 | 读取方式 |
| --- | --- | --- |
| 显示正则 | 随楼层；静态排版 | 经宿主 HTML 净化，无脚本 |
| 楼层 HTML 代码块 | 随楼层；本楼交互 | 同源 iframe；宿主公开 API 从 `window.parent` 访问 |
| 循环任务 `<<taskjs>>` | 后台动作或跨楼层常驻界面 | 运行于酒馆页面，使用 `window`、`document`、`SillyTavern.getContext()` |

触发时机、停止条件和清理见[能力参考](<../references/xiaobaix-capabilities.md>)第 2～4 节。图片、地点表等共享数据由常驻任务保留一份，各楼按需读取。

## 视觉与表现力

先定玩家此刻第一眼该看哪里。入场时可以把整屏交给一个场景；读故事时，让正文落在安静、对比清楚的底上；做选择时，让同等可选的行动和各自的后果容易比较。

把最浓的色彩、材质或动作留给这张卡独有的人、物或事件。底色和普通控件沿用同一组色调，强调色留给当前选择或关键动作；警示等状态色有固定含义，同时用文字或形状说明。用对齐和留白分组：选项与它的代价靠近，不同选择之间拉开。层次已经清楚的地方，无需再套一层框。

新界面的视觉设计用本节即可。只有审视已有画面，或玩家指出「太花」「太挤」「没重点」「AI 味重」时，才读[视觉诊断](<visual-review.md>)。

## 按当前目标组织实现

下面是前端制作的几个工作面，按用户要先看到的结果和已有内容选择、组合。

- **阅读与行动**：用真实正文和一次完整行动安排画面。桌面与手机都能读、能操作，行动后能直接看见回应。
- **宿主衔接**：接入本卡使用的发送、重写、变量和图片操作；界面接管了哪部分体验，就保留那部分操作与反馈。保留输入草稿，显示生成中、失败与取消。
- **数值**：显示实际提交后的结果，刷新页面不再次结算。见[变量刷新](<../references/xiaobaix-capabilities.md#state-panel-refresh>)。
- **媒体**：服务失败时保留已有结果，不自动重复付费请求。
- **检查**：按[交互验收](<../references/xiaobaix-capabilities.md#frontend-validation>)检查与本次改动有关的操作。一体界面还要在不退出的情况下完成一轮阅读、发送和结果查看；收起、重开、重绘后所用宿主功能仍可操作。报告实际检查到的范围。
